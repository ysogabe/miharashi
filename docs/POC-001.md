# PoC-001 Rust Direct Display 結果

目的: LinuxのDRM/KMSをRustから直接操作し、写真・日本語テキスト・時系列グラフを同一画面に描画しながら、キーボードで画面を切り替えられること。X11・Wayland・ウィンドウマネージャーには依存しない。

検証日: 2026-10-11〜12 / ブランチ: `trial/poc-001-direct-display`

## 環境

| 項目 | 内容 |
|---|---|
| ホスト | geoframe-n100(Debian 13、Linux 6.12) |
| 表示 | NVIDIA RTX 5060 Ti(nvidia-drm、`modeset=Y`)の `HDMI-A-1`、1920×1080@60Hz |
| 入力 | Lenovo ThinkPad Compact USB Keyboard(テンキーなし) |
| 実行ユーザー | 一般ユーザー(`video`・`input` グループ) |
| 写真 | GEOFRAME `GET /api/photos` と `GET /derivatives/*.jpg`(1600×1200 JPEG) |

内蔵Radeonは今回のホストでは見えなかった(BIOSでiGPU無効の可能性)。表示はdGPU経由。

## 合否

| 項目 | 結果 | 根拠 |
|---|---|---|
| P0 DRM/KMS検出 | 合格 | `kms-info` が card0(nvidia-drm)・HDMI-A-1接続・1920×1080@60を列挙 |
| P1 PNG生成 | 合格 | 1920×1080のPNGを2枚生成(約0.75秒、写真取得込み) |
| P2 テキスト・画像・グラフ合成 | 合格 | 日本語、写真(cover切り抜き)、折れ線+塗り、半透明帯を目視確認 |
| P3 KMS直接出力 | 合格 | dumb bufferで表示。乱れ・色の入れ替わりなし(目視) |
| P4 キー入力 | 合格 | `←`/`→`/`4`/`6` で2画面が切り替わる。4/6を交互に10回ずつ押して20件記録(一致)。KP4/KP6は未検証 |
| P5 動的描画 | 合格 | 1秒ごとに数値・グラフ・時計が更新。キー操作は即時反映 |
| P6 復旧・終了 | 合格 | 60秒/30分の終了後にLinuxコンソールへ復帰(目視) |

## 測定

30分連続表示を2回実施。

| 項目 | 1回目(システムフォント) | 2回目(`--font` でヒープ読み込み) |
|---|---|---|
| 完走 | 1800秒、1810フレーム、exit 0 | 結果は末尾に追記 |
| フレーム時間(通常) | 6〜7ms | 6〜8ms |
| RSS | 51MB → 17MB(後述) | 49MB → 14MB(後述) |
| CPU使用率 | 約0.7%(開始150秒の実測のみ) | 1分ごとにCPU時間を記録 |
| GPU使用率 | 0%(`nvidia-smi`、GPUプロセスなし) | 同左 |

### フレーム時間の揺れの原因

1回目の570秒以降と2回目の約75秒以降、フレーム時間が約7msと約80msで交互に出た。RSSも急減した。

- 別プロセス(`strata`、RSS約29GB)がホストのメモリ約26GB/31GBを使用しており、空きが約290MB。
- このアプリのメモリがスワップへ出ていた(`VmSwap` 約31MB)。読み戻しで1フレームあたり約80ms。
- 1回目は、他プロセスによる `drop_caches` がカーネルログに3回あり、時刻が揺れの時間帯と一致した。
- ヒープへのフォント読み込みでは解消しなかった。レンダラー自体の問題ではなく、メモリ逼迫した共用ホストの影響と判断する。
- 揺れは最大約90msで、1秒周期の更新には影響しなかった。

## 画面確認方法

```
cargo build --release
./target/release/miharashi-poc png --geoframe http://127.0.0.1:8080    # PNG(work/out/)
./target/release/miharashi-poc kms-info                                 # DRM列挙
sudo -u hermes ./target/release/miharashi-poc kms-show --seconds 60     # 実機表示
```

`sudo -u hermes` はグループ変更をログイン前に反映するための手段。再ログイン後は直接実行できる。`sg` の入れ子は補助グループを引き継がないため使えない。

## 未検証

- 物理テンキーのKP4/KP6(コードは対応済み)。
- 連打・同時押し時の取りこぼし。4/6を交互に10回ずつ(計20回)押した条件では、記録20件で一致し、二重記録もなかった。1回目の「約9回押下に対し6件」は、回数を数えずに押した概算で、判定には使えない。
- 30分通しのCPU使用率(1回目は開始150秒のみ、2回目で取得)。
- 内蔵Radeon表示、複数GPUでのデバイス選択。
- seat管理(libseat)、systemd自動起動、VT切替での解放。

## MVPへの課題

1. メモリ逼迫下の遅延対策。専用機ではスワップが起きにくいが、`mlockall` を使う場合は `LimitMEMLOCK` を設定する。フォント(19MB)は8MBの既定上限を超える。必要な字形だけのサブセット化も候補。
2. 入力デバイスの絞り込み。キーボード本体のノードだけを開く(二重記録は確認されていない)。連打条件での取りこぼし検証を実施する。
3. DRMデバイスを `/dev/dri/card0` に固定しない。KMSモードの選択を設定にする。
4. 描画のたびに `cosmic-text` のバッファを作り直している。静的テキストのキャッシュと、変更領域だけの再描画を検討する。
5. 実際のCPU/GPU/メモリ取得(NVML等)。画面の数値は現在ダミー(正弦波)。
6. seat・権限管理(libseat、VT往復)。rootなしでの運用方法の確定。
7. 写真取得元(GEOFRAME)の設定化と、取得失敗時のフォールバック。写真は個人データのためリポジトリへ含めない。
8. 内蔵GPU有効化後に、表示用GPUと計算用GPUの選択を再検証する。
