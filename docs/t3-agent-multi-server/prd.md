# T3 Agent 複数サーバー PRD

状態: 検討案（2026-11-06）。実装・実接続の変更は未実施。

## 背景と目的
既存 T3 Agent は1台を監視する。既存接続を保ち、最初の追加先として `lxc-t3code` コンテナの t3-server を同じ画面で監視したい。

## 使う人と場面
キオスクで複数の T3 Server の稼働・承認待ち・入力待ちを一目で確認する利用者。

## ゴール / やらないこと
ページを増やさず、全接続先を同時に確認できること。サーバー切替による別ページ化、自動巡回、T3への更新操作、コンテナ作成やネットワーク設定変更はmiharashiの実装範囲外。ただし到達性・公開範囲・接続先固定を本番接続の前提として確認する。

## 要求
- R1（必須）: 既存 `agents` 画面1枚に全サーバーのスレッドを統合表示する。
- R2（必須）: 各カード・プロジェクト見出し・変更通知から接続先を識別できる。
- R3（必須）: 接続・認証・再同期・stale判定をサーバー単位で独立させる。1台の停止で他を止めない。
- R4（必須）: 同一 thread/project ID が別サーバーにあっても、親子関係・通知・描画キャッシュを混同しない。
- R5（必須）: 旧設定で従来どおり1台に接続できる。複数接続は追加設定で有効にし、既存のtoken自動更新を維持する。
- R6（必須）: 各接続の認証情報を分離し、既存のURL・トークン保護を維持する。
- R7（必須）: 最初の追加先をコンテナ内サーバーとし、接続前に到達性・API互換性・認証運用を確認し、追加先のtoken更新と更新失敗の検知まで確かめる。
- R8（必須）: 表示容量超過でも重要状態を優先し、未表示件数とサーバー別接続状態を表示する。

- R9（必須）: 既存の管理Webページ内で、接続ごとの取得状態とtoken状態を確認できる。接続数の上限は既存を含め4台。

## 受け入れ条件
- AC1（R1,R2）: 2台のfixtureを同一screen ID `agents` に表示し、各カード・通知の接続先が判別できる。追加画面登録は0件。
- AC2（R3）: 片方の遅延・401・切断・再同期中も他方の更新と通知が継続する。障害側の最終データに「前回取得時」と表示される。stale_secs超過後はその接続の通知だけを停止する。
- AC3（R4）: 2台に同じproject/thread/parent IDを与えても別カードとなり、他サーバーの親子や通知に結合されない。
- AC4（R5）: 旧設定の接続数は1。extra_servers追加で2台を登録でき、重複ID・予約ID primary・不正label・合計5台以上を拒否する。追加配列の省略/空は従来どおり1台。
- AC5（R6）: 接続ごとに別tokenで認証し、リダイレクトや別originへtokenを送らない。不正URL・token権限のテストが通る。
- AC6（R7）: 固定アドレスまたは証明書検証付きHTTPS名、既存LAN接続を維持した待受/ファイアウォール、T3 v0.1.0以降とorchestration:read権限を確認した上で、実装後、既存先とコンテナ先で認証済みshell取得成功、両者の画面表示、片方の停止・復帰を実機確認する。移行後も既存timerのtoken更新が成功し、追加先もtoken更新・再読み込み・更新失敗表示が確認できる。確認前は本番対応済みと報告しない。
- AC7（R8）: 4台・小解像度・VRM併用・多件数・長い接続名でも見出しが重ならず、重要状態の優先順位と未表示件数が正しい。

- AC8（R9）: 管理Webで2台の取得成功/401と、token正常/欠落をそれぞれ分けて表示する。新しいページは追加しない。

## 制約
既存の Rust worker / Provider / AgentScreen を拡張する。認証情報の値・実IPは文書やログに書かない。管理Web画面もページを追加しない。

## 決まっていないこと
コンテナのIP/ポート・待受・T3バージョン・到達性、token発行と更新の実運用。コンテナ調査はLXDソケットへの権限不足で未完了。実装時の必須確認として扱う。

2026-11-07のユーザー指定: 既存LAN接続を維持する。監視ホスト限定への変更は行わない。固定アドレス・認証と読み取りscopeは引き続き必須。
