## 1. 前提: 常用モニターと解像度

常用モニターは **LG 29UM59-P**(29インチ、21:9、IPS、2560×1080)。

現在の画面は、1920×1080 を基準にした**固定ピクセル**のレイアウトである(ヘッダー 72px、タイル高さ 220px、文字 72px/36px など)。変わるのはタイルの横幅とグラフの大きさだけ。各解像度でPNGを描画して確認した結果:

| 解像度 | 状況画面 |
|---|---|
| 1920×1080 | 想定どおり |
| **2560×1080(常用)** | **崩れない**。高さが同じで、タイルとグラフが横に伸びるだけ。文字の重なりなし |
| 1280×720 | ほぼ問題なし。FAN タイルでラベルと値が重なる |
| 1024×768(4:3) | SSD・FAN タイルでラベルと値が重なる |
| 3840×2160(4K) | 文字・タイルが小さく見え、グラフが間延びする |

結論: 常用モニターでは状況画面のレイアウト修正は不要。1024×768 や 4K 向けのスケール対応(高さ基準の係数、文字幅を測った配置)は、優先度を下げる(別Issueで扱う)。2560×1080@60Hz を HDMI-A-1 が出せるかは、実機で未確認(`display.mode = "2560x1080@60"` で固定できる)。

写真の表示は `cover`(拡大して切り抜き)のため、21:9 では上下が大きく切れる。

| 写真の比率 | 2560×1080 で見える範囲(縦) |
|---|---|
| 4:3 | 56% |
| 3:2 | 63% |
| 16:9 | 75% |

## 2. フォトフレームの新しい表示

### 決定事項(ユーザー回答)

| 項目 | 決定 |
|---|---|
| 横向きの写真 | **高さ 1080 に合わせて全体を表示**し、空いた左右に情報を出す |
| 写真の位置 | **左 → 右 → 中央**の順に巡回する(焼き付き・残像の防止) |
| 余白の背景 | **写真を拡大してぼかした背景** |
| 時刻・日付 | **常に大きく表示**する |
| 写真の情報 | 場所・撮影日時・位置(n / N)は、時刻・日付の下に小さく表示 |

### 写真の比率ごとの扱い(2560×1080)

| 写真の比率 | 写真の幅 | 空き | 配置 |
|---|---|---|---|
| 4:3 | 1440px(56%) | 1120px | 左 / 右 / 中央を巡回 |

巡回の順序は、写真の比率に関わらず「左 → 右 → 中央 → 左…」。ただし、その配置が選べない比率(16:9 の中央)は飛ばして次へ進む。

### 実装方針

- **時刻**: 秒は出さず `HH:MM` のみ(約200px級の文字)。更新が分単位で済み、焼き付き防止にも向く。日付は時刻の下に大きく(約60px級)。
- **ぼかし背景**: 写真を全面に拡大し、縮小 → ぼかし → 拡大 → 暗めに調整して作る。写真と合成した**完成フレームを、写真を読み込むスレッドで1枚につき1回だけ作る**。毎フレームの描画は、完成した1枚の絵を貼るだけにして、現在の描画の軽さを保つ。
- **焼き付き対策の補助**: 時刻・日付の位置を、1分ごとに数ピクセルずらす。
- **フェード**: 切替時のクロスフェードは現在どおり。位置が変わるため、旧フレームと新フレームをそのまま重ねる。
- **撮影日の相対表記**(「7か月前」)を追加する。撮影日時が空の写真は、相対表記と撮影日の行を出さない。
- **場所**: 現在どおり GEOFRAME の `pref` と `title` を使う。

未検証: 4:3 と 16:9 を高さ 1080 に合わせたときの実際の見た目、ぼかしの強さ・暗さの調整値、ぼかし背景の合成にかかる時間(2560×1080 で見積り要)、メモリ(完成フレームを旧・新の2枚保持した場合の合計。2560×1080 の1枚は約11MB)。

## 3. Server Status の拡張

### 3.1 消費電力(CPU・GPU)

| 対象 | 取得方法 | このホストでの状況 |
|---|---|---|
| GPU の W | NVML の消費電力。権限不要 | 取得可(確認時 7.7〜8W、上限 180W) |
| GPU の積算 | NVML の積算エネルギー、または W の自前積算 | 積算エネルギーの対応は未確認。自前の積算なら確実 |
| CPU の W | RAPL(`/sys/class/powercap/intel-rapl:0`、`package-0`)の積算エネルギーの差分 | センサーあり。ただし `energy_uj` は root 限定(0400) |
| CPU の積算 | 差分の自前積算(カウンターのラップ処理が必要) | 取得可の見込み |
| PC 全体(コンセント側) | ソフトだけでは不可。スマートプラグ・UPS・電力計が必要 | hwmon に電力センサーなし。`upsc` 未導入。**手段が決まっていない** |

CPU 電力の読み取り権限の方式(推奨は **a**):

- **(a) 専用の root ヘルパー**が `energy_uj` を読み、`/run/miharashi/` に書き出す。キオスク本体は一般ユーザーのまま。最小権限。
- (b) キオスクに `CAP_DAC_READ_SEARCH` を与える。権限が広すぎる。
- (c) `energy_uj` を全員に読ませる。RAPL を root 限定にしている電力解析の攻撃(Platypus)対策に反するため避ける。

精度の注意: AMD の RAPL は測定値ではなくモデルによる推定で、CPU 全体(コア + I/O)の目安である。メモリやマザーボードは含まない。画面には「CPU+GPU のみ」と明記し、CPU の W に `*`(推定)を付ける。

電力量(Wh):
- 起動をまたぐ累計は `/var/lib/miharashi/`(`StateDirectory`)に定期保存する。カウンターの巻き戻り(再起動、ドライバー再読込)に影響されないよう、差分を自前で積算して保存する。
- 表示は「今日」と「累計」。電気代は `config` に単価がある場合だけ表示する。

### 3.4 実装方針

- 新しい指標は `DataSource` と `Snapshot` に項目を足す形で追加する。実行ループ(`runtime.rs`)は変更しない。取得できない項目は `--` と表示する(現在と同じ)。
- 収集は、指標ごとにバックグラウンドスレッドで行う。ネットワークやディスクなど、差分が必要なものは前回値を保持する。
- 画面側は、PoC-003(画面追加の共通インターフェース)と衝突しないよう、`KioskApp` の中でページ切替を持たせる。
- ページ数は、2560×1080 の広さに応じて決める(1ページに収まるなら、2ページにしない)。
