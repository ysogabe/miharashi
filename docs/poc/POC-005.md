## 計測方法

### 状態ログ(実機)
`stats:` 行の末尾に次の値を足した(既存の並びは変えていない。`tools/soak_summary.py` が集計する)。

| キー | 意味 |
|---|---|
| `cpu_self` | 区間内の自プロセスの CPU 使用率 [%]。全スレッドの合計で、1 コア = 100%。`/proc/self/stat` の utime+stime の差分 |
| `render_ms` | 区間内の描画(`App::render`、tiny-skia で Canvas に描く)の時間。`平均/p95` [ms] |
| `present_ms` | 区間内の転送(Canvas から dumb buffer への XRGB8888 変換コピー)の時間。`平均/p95` [ms] |
| `gpus` | GPU ごとの使用率(#15)。iGPU は GPU1 |

集計: `sudo journalctl -t miharashi -o short-iso --since "<開始>" | python3 tools/soak_summary.py`

### bench(ヘッドレス)
`miharashi bench [--size WxH] [--frames N] [--photo FILE]`。各場面を N 回(写真の処理は最大 5 回)描いて、1 回あたりの CPU 時間を出す。最初の 1 回は捨てる。`--photo` を省くと、4032×3024 の合成写真(ノイズ入りのグラデーションを JPEG にしたもの)を使い、ネットワークに依存しない。

| 場面 | 何を測るか | 実機での頻度 |
|---|---|---|
| `status-overview` / `status-details` | 状況画面 1 枚の描画 | 1 秒に 1 回 |
| `photo-static` | 写真画面 1 枚の描画(完成フレームの貼り付けと文字) | 1 秒に 1 回(時刻の更新) |
| `photo-fade` | クロスフェード中の 1 枚(新旧 2 枚の合成と文字) | 写真の切り替えごとに 800ms の間、描画のあと 20ms 待って次を描く |
| `present-xrgb8888` | XRGB8888 への変換コピー(メモリ上。実機の dumb buffer は `present_ms` を見る) | 描画のたび |
| `photo-decode` | JPEG のデコード | 写真 1 枚ごと(既定 30 秒に 1 回) |
| `photo-blur-bg` | ぼかし背景の生成 | 写真 1 枚ごと |
| `photo-compose` | デコード、配置、ぼかし背景、写真の縮小、合成の全部(取得スレッドの処理) | 写真 1 枚ごと |

## CPU 経路のベースライン(PR1)

### bench(2026-10-13、release ビルド、合成写真 4032×3024)

| 場面 | 1920×1080 平均 [ms] | 2560×1080 平均 [ms] |
|---|---:|---:|
| status-overview | 5.20 | 5.84 |
| status-details | 3.43 | 3.70 |
| photo-static | 6.27 | 8.37 |
| photo-fade | 12.82 | 17.18 |
| present-xrgb8888 | 0.77 | 1.03 |
| photo-decode | 63.5 | 63.4 |
| photo-blur-bg | 35.6 | 42.4 |
| photo-compose | 216 | 225 |

p95 は、どの場面も平均との差が 2% 以内だった。

### 読み取れること
- **定常時(1 秒に 1 回の描き直し)は軽い**。2560×1080 で状況画面は約 6ms+転送 1ms なので、1 コアの約 0.7%。
- **クロスフェードが一番重い**。実行ループは描画(17ms)と転送(1ms)のあと 20ms 待つので、周期は約 38ms。800ms のフェードで約 21 枚描き、その間は **1 コアの約半分** を使う。フェード 1 回で CPU 約 0.38 秒。写真を 30 秒ごとに替えると、平均で 1 コアの約 1.3% になる(推定。実機の値は下の 1 時間計測で確かめる)。GPU で新旧 2 枚を混ぜれば、CPU は文字の描き直しだけになる(PR3 の主な狙い)。
- **写真 1 枚ごとの処理は約 225ms**(デコード 63ms、ぼかし背景 42ms、残りが Lanczos3 による写真の縮小と合成)。30 秒に 1 回なので、平均で 1 コアの約 0.75%。縮小とぼかしは GPU に移せる(PR3)。デコードは CPU に残る(VCN の JPEG デコードは PR4 で検討)。

### 実機の 1 時間計測(2026-10-13 14:42〜15:42、2560×1080)
PR1 のバイナリ(1f8c470)を本番に入れて 1 時間動かした。途中で画面を切り替えたので、`key:` の行で区間を分けて集計した。値は 1 分ごとの `stats:` 行の中央値。

| 区間 | 時間 | 画面 | `cpu_self` [%] | `render_ms` 平均/p95 | `present_ms` 平均/p95 | 描画回数/分 |
|---|---|---|---:|---:|---:|---:|
| 状況画面 | 14:44〜15:15(31 分) | Status(Overview) | 1.0 | 2.8 / 3.2 | 1.6 / 1.6 | 60 |
| 写真画面 | 15:16〜15:42(27 分) | Photo(30 秒ごとに切り替え、27 分で 54 枚) | 3.3 | 12.5 / 17.7 | 1.6 / 1.6 | 約 100 |

全体(soak_summary): `cpu_self` 平均 2.10%、フレーム時間の区間最大は 21ms、100ms 超は 0 回、更新停止 0 件、fd は 26〜27 で一定。

スレッドごとの CPU 時間(終了時点、`/proc/<pid>/task/*/stat`、稼働 3609 秒、合計 75.9 秒 = 1 コアの 2.1%):

| スレッド(起動順) | utime [s] | stime [s] | 合計 [s] | 役割(推定) |
|---|---:|---:|---:|---|
| 1 番目(メイン) | 52.3 | 3.2 | 55.5 | 描画と転送の実行ループ |
| 2 番目 | 0.4 | 12.9 | 13.3 | 監視(NVML と sysfs の読み取り)。ほぼカーネル時間で、画面に関係なく 1 コアの約 0.37% |
| 3 番目 | 6.9 | 0.2 | 7.1 | 写真の取得と合成 |
| cuda0000240000a | 0 | 0 | 0 | NVML が作るスレッド(何もしていない) |

スレッドの名前はどれも `miharashi` なので、役割は起動順と utime/stime の比から推定した。

CPU パッケージの電力(RAPL、写真画面の表示中に 60 秒間): 22.8W。システム全体の値なので、miharashi の分は切り出せない。PR3 の後に同じ条件で測って比べる。iGPU の使用率(`gpu_busy_percent`、GPU1)は全区間で 0%。CPU 経路では iGPU は走査出力しかしていない。

#### 読み取れること
- **状況画面は 1 コアの 1.0%**。描画 2.8ms と転送 1.6ms を 1 秒に 1 回で 0.44%、残りは監視スレッド(0.37%)など。
- **写真画面は 1 コアの 3.3%**。状況画面との差は 2.3% で、写真 1 枚あたり CPU 約 0.69 秒になる。内訳の見積もりは、フェード約 20 枚(描画回数が 1 分あたり 40 回増え、1 分に 2 回切り替えている)×(17ms+1.6ms)で約 0.37 秒、写真の合成(bench で 225ms)で約 0.23 秒、合計約 0.6 秒。実測とおおむね合う。
- bench で推定した写真画面の平均(フェード 1.3%+合成 0.75%)より実測の差分(2.3%)が少し大きい。写真画面の静止時の描画(bench で 8.4ms)が状況画面(2.8ms)より重い分が上乗せされている。
- **転送は実機の dumb buffer で 1.6ms**。bench(メモリ上のコピー)の 1.03ms より約 55% 遅い。dumb buffer が write-combine の領域にあるためと考えられる。描画回数に比例するので、フェード中はこの分も効く。
- **GPU に移すと減らせるのは主に写真画面の 2.3%**(フェードの合成と転送、写真の縮小とぼかし)。状況画面の 1.0% のうち監視スレッドの 0.37% は描画と関係がない。
- RSS は写真画面で 119MB から 184MB まで増えた(途中で 88MB に下がった時点もある)。写真のバッファの確保と解放によるもので、PoC-002 の 12 時間試験では増え続けなかった。PR3 の 12 時間試験でもう一度確かめる。

## GLES 表示経路(PR2)

### 作ったもの
- 新しいクレート `crates/miharashi-gpu`(Linux 専用)。
  - libseat から受け取った表示カードの fd の上に、GBM device、GBM surface(XRGB8888、走査出力と描画の両用)、EGL(platform GBM)、GLES 3.2 のコンテキストを作る。
  - CPU で描いた Canvas(RGBA8)を毎回テクスチャに転送し、全画面の三角形を 1 枚描く。拡大縮小しないので NEAREST でサンプリングする。
  - `eglSwapBuffers` のあと GBM の前面バッファを framebuffer にし、最初の 1 枚は `set_crtc`、以後は `page_flip`(イベント付き)で切り替えて完了まで待つ。framebuffer は GEM ハンドルごとに使い回す。
  - VT の切り替え(suspend / resume)と終了時の CRTC の復元は、dumb buffer の経路と同じ動き。
- `gbm` クレートは drm 0.14 に依存していて、このワークスペースの drm 0.15 と型が合わないので、`gbm-sys` を直接呼ぶ。libEGL は実行時に読み込む(`khronos-egl` の dynamic)。
- `kms.rs` のコネクター、モード、CRTC の選択を `Output` に切り出し、両方の経路で使う。
- 設定 `[display] renderer = "cpu" | "gles" | "auto"`。既定は `cpu`。`auto` は GLES を試し、使えなければ理由をログに出して `cpu` に戻る。
- `miharashi png --renderer gles`: 3 画面を表示と同じシェーダーで表示カードの render node に描いて読み戻し、`*-gles.png` に保存して CPU 版との画素の差を出す。

### 実機で確認(2026-10-13)
| 項目 | 結果 |
|---|---|
| コンテキスト | `OpenGL ES 3.2 Mesa 25.0.7 / AMD Radeon Graphics (radeonsi, raphael_mendocino)`。描画は内蔵 GPU だけ |
| 画素の一致(`png --renderer gles`、2560×1080) | 状況 2 画面と写真画面で、差のある画素 0 / 2,764,800 |
| 目視 | 状況画面と写真画面(フェードを含む)が CPU 経路と同じに見える |
| VT の切り替え | `sudo chvt 2` → `chvt 7` で、描画の停止、入力の開き直し、表示の復元を確認 |
| 物理キーボードの Ctrl+Alt+Fn | 効かない(CPU 経路でも同じ)。libseat(logind)がセッションを持つと VT のキーボードが止まり、切り替えはプログラム側で行う必要がある。本番ではキーボードをつながないので対象外 |

### 実機の 1 時間計測(2026-10-13 16:08〜17:08、2560×1080、`renderer = "gles"`)
PR1 と同じ方法で、区間を `key:` の行で分けて集計した。

| 区間 | 経路 | `cpu_self` 平均 / 中央値 [%] | `render_ms` 中央値 | `present_ms` 中央値 | 描画回数/分 |
|---|---|---:|---:|---:|---:|
| 状況画面(30 分) | CPU(PR1) | 1.0 / 1.0 | 2.8 | 1.6 | 60 |
| 状況画面(30 分) | GLES | 1.1 / 1.0 | 3.7 | 8.1 | 60 |
| 写真画面(27 分) | CPU(PR1) | 3.3 / 3.3 | 12.5 | 1.6 | 約 100 |
| 写真画面(29 分) | GLES | 3.2 / 2.9 | 12.1 | 12.5 | 約 92 |

その他(GLES): RSS は 299〜302MB で一定(CPU 経路は 119〜184MB)。fd は 29〜30 で一定。更新停止 0 件。GPU ドライバーのスレッド(`miharashi:cs0` など)の CPU 時間は 1 時間で合計 0.4 秒。

#### 読み取れること
- **CPU 使用率は CPU 経路とほぼ同じ**。PR2 は表示の仕組みを替えただけで、毎回 Canvas 全体(2560×1080×4 = 11MB)を CPU で描いて GPU に転送している。XRGB8888 への変換コピー(1.6ms)はなくなったが、代わりにテクスチャへの転送(ドライバー内のコピー)が入るので、差が出なかったと考えられる。CPU を減らすのは PR3(フェードの合成を GPU で行い、変わった部分だけを転送する)の仕事。
- **`present_ms` が大きいのは、page flip の完了(次の垂直同期、60Hz で最大 16.7ms)を待つ時間が入っているため**。待っている間は CPU を使わない。CPU の負荷は `cpu_self` で比べる。
- 写真画面の描画回数が 1 分あたり約 100 回から約 92 回に減った。フェード中は 1 枚ごとに垂直同期を待つので、1 枚の周期が延びた(フェード 1 回で約 20 枚 → 約 16 枚)。フェードは 800ms のまま。
- **RSS は約 120〜180MB 増えたが、1 時間増え続けなかった**。Mesa の radeonsi と LLVM(シェーダーのコンパイラー)を読み込む分。PR3 の 12 時間試験でもう一度確かめる。
- 計測の途中で、別の処理が NVIDIA GPU を使っていた(16:18〜16:31 ごろ GPU0 が 98〜100%)。その間は `render_ms` が 3ms から 5〜7ms に延びたが、`cpu_self` はほとんど変わらなかった。16:20〜16:21 の 2 回、iGPU(GPU1)の使用率が 100% と出た。miharashi は 1 秒に 1 回しか描いていないので、ほかの要因と思われるが、原因は確かめていない。

## GPU 合成(PR3a)

PR3 は 2 つに分けた。PR3a はクロスフェードと重ね絵の合成を GPU に移す。PR3b は写真の縮小とぼかし背景を GPU に移す(未実施)。

### 作ったもの
- `miharashi-gpu` の `Compositor`(`compose.rs`)。
  - 写真画面は 3 層で描く。写真フレーム(新)、写真フレーム(旧、フェード中だけ)、重ね絵(時刻、日付、写真の情報、通知)の順。
  - 写真フレームは取得スレッドが作った完成フレームをそのまま使い、通し番号ごとに 1 回だけテクスチャに転送する(直近 3 枚を保持)。
  - フェードはシェーダーで `mix(旧, 新, t)` を計算する。CPU 経路の「旧を描いてから新を不透明度 t で重ねる」と同じ式。
  - 重ね絵は透明背景の Canvas(乗算済み RGBA)に CPU で描き、内容が変わったときだけ転送する。重ねるときのブレンドは `ONE, ONE_MINUS_SRC_ALPHA`。
- `App::render_composite`(PoC-005 の内部用。#5 で画面の API が決まったら合わせる)。
  - 写真画面では写真と重ね絵を分けて返す。
  - 重ね絵を描き直すのは、1 秒ごとの更新、キー入力、写真の切り替えのときだけ。フェード中の毎フレームは描き直さない。
  - 状況画面は今までどおり Canvas 全体を描いて転送する。
- `photo_frame` から重ね絵の部分を `photo_overlay` に切り出した。CPU 経路の見た目は変わらない。
- bench に `photo-overlay`(透明な Canvas に重ね絵だけを描く。GPU 経路で CPU に残る仕事)を追加した。

### 確認したこと
| 項目 | 結果 |
|---|---|
| 単体テスト(offscreen、render node) | フェード(t=0.25)と半透明の重ね絵の合成が、CPU の式と ±1 で一致。重ね絵を渡さない回は前回の重ね絵を使う |
| 単体テスト(app) | 「写真+重ね絵」を CPU で重ねた結果が `render()` と最大差 2 で一致 |
| `png --renderer gles`(写真画面、2560×1080) | 合成経路で描いた結果と CPU 版の差: 差のある画素 2,072 / 2,764,800、最大差 1(乗算済みアルファの丸め) |
| 目視(実機) | フェードと文字が CPU 経路と同じに見える |

#### 読み取れること
- **写真画面の CPU が半分以下になった**(平均 3.2% → 1.5%)。フェード中も 1 枚あたりの描画は 0.4ms で、CPU は重ね絵の描き直し(1 秒に 1 回)と GPU への命令だけを担当する。
- 状況画面との差は約 0.6%。ほとんどは取得スレッドの写真の合成(bench で 1 枚 225ms、30 秒に 1 回で約 0.75%)。これを PR3b で GPU に移す。写真画面の中で `cpu_self` が 1.1% の時間と 1.9% の時間がある。当初は写真ごとの合成の重さの違いと考えたが、PR3b(取得スレッドの合成をなくした後)でも同じ段差が出たので、原因は別にある([PR3b](#写真の合成を-gpu-でpr3b) を参照)。
- 描画が軽くなったので、フェード中の描画回数は PR2 の約 16 枚から約 23 枚に増えた(1 分あたり約 107 回)。周期は「20ms 待つ+垂直同期を待つ」で決まる。
- 状況画面は PR2 と同じ仕組み(Canvas 全体を毎回転送)なので、差は誤差の範囲。状況画面の描き直しを減らすのは今回の範囲外。
- 18:27〜18:32 に GPU0(NVIDIA)が 74〜98% になった(別の処理)。その間も iGPU(GPU1)は 0% のままで、写真画面の `cpu_self` は変わらなかった。状況画面に切り替えた直後の 18:31〜18:35 は `render_ms` が 4〜9ms に延びた(PR2 でも同じ現象を確認している)。

## 写真の合成を GPU で(PR3b)

### 作ったもの
- GPU 経路では、取得スレッドは写真のデコードと配置の決定(`photo_layout::plan`)だけを行い、デコードした写真(RGB8 か RGBA8)をそのまま渡す。CPU 経路は今までどおり取得スレッドで完成フレームまで作る。
  - 描画ループが GLES で開けたときだけ GPU 経路にする(`auto` で CPU に戻ったときは CPU 経路)。
  - `GL_MAX_TEXTURE_SIZE`(このホストは 16384)を超える写真は、CPU で完成フレームまで作る。
- `miharashi-gpu` の `PhotoBuilder`(`photo.rs`)が、写真 1 枚につき 1 回、画面と同じ大きさの完成フレームをテクスチャに描く。合成器はそれを PR3a と同じ写真の層として使う(直近 3 枚を保持)。
  - 手順は CPU 経路(`compose_image`)をそのままシェーダーで再現した。
    1. Lanczos3 の縮小を縦 → 横の順に行う(image クレートと同じ標本化、途中は RGBA16F)。
    2. ぼかし背景は、面積平均の縮小(`thumbnail` の代わり)→ 1/16 の大きさに中央切り抜き → 箱型ぼかし(半径 3、縦横 3 回)→ 双一次で拡大 → 明るさ 0.42 倍。
    3. 10 段の影を落として写真を置く。
  - 計画では dual Kawase ぼかしにする予定だったが、「CPU 経路と同じ見た目」を合格の条件にしたので、CPU と同じ箱型ぼかしにした。
- デコードした写真の画素は、GPU に 1 回渡したら CPU 側から捨てる。12MP の写真で 1 枚約 36MB あり、フェード中は新旧 2 枚を持つため。
- 状態ログに `photo_gpu_ms`(写真 1 枚の完成フレームを作るのにかかったメインスレッドの CPU 時間。`平均/p95`)を追加した。

### 確認したこと
| 項目 | 結果 |
|---|---|
| 単体テスト(offscreen、合成画像、1920×1080) | `compose_image` との差は最大 1。左寄せ(ぼかし背景と影あり)と画面いっぱい(cover)の両方で、写真の部分と背景の部分を分けて比べた |
| 単体テスト(app) | 1 回目はデコードしただけの写真を渡し、2 回目からは GPU 側のものを使う。上限を超える写真は完成フレームになる。CPU の `render` でも描ける |
| `png --renderer gles`(GEOFRAME の実写真、2560×1080) | 差のある画素 322,108 / 2,764,800、最大差 2 |
| 目視(実機) | フェード、ぼかし背景、影が CPU 経路と同じに見える。写真の切り替えで引っかかりは見えない |

## 航空機のレーダー画面(PR4a)

12 時間試験で、航空機の画面を表示している 1 分間は `cpu_self` が 13〜14% になっていた。中身が止まった画面を CPU で毎回全画面描き直していたため。これを、空港の管制レーダーのような「暗い背景に緑の線」の画面に作り直し、回る線と残光を GPU で描くようにした。

### 作ったもの
- 見た目
  - 暗い背景に緑の距離環、方位線、地図。注目している機体だけは今までどおり琥珀色にする。
  - 線は 4 秒で 1 周する(`SWEEP_PERIOD_SECS`)。後ろに 0.9 rad の残光を引く(`TRAIL`。3 案を画像で比べて、ユーザーが中間の案を選んだ)。
  - 機体の点は、線が通ったときに明るくなり、残光と一緒に暗くなる。
- 描き分け
  - CPU(`miharashi-render` の `aircraft.rs`)は、線と点を除いた画面(背景、地図、機体の名前と表)だけを描く。中身は 5 秒ごとの機体の更新のときだけ変わる。
  - 地図の層(距離環、方位線、海岸線)は `RadarBase` として持ち続ける。機体が更新されたときは文字と表だけを描き直す(1 回 7.6ms → 4.7ms)。
  - GPU(`miharashi-gpu` の `compose.rs`、`FRAG_RADAR`)は、背景のテクスチャの上に、回る線、残光、点(最大 32 個)を加算合成で毎フレーム描く。背景のテクスチャは中身が変わったときだけ送り直す。
  - CPU 経路(`renderer = "cpu"` か GLES で開けなかったとき)は、線を止めた 1 枚を描き、機体が更新されたときだけ描き直す。
- 描く周期
  - レーダーを表示している間は、描画ループの 20ms の待ちを外し、垂直同期だけで回す(60fps)。最初は 20ms の待ちを残していたので 30fps になり、背景も描き直す回は 50ms 間があいて、回転が引っかかって見えた。
  - `App::animating()` が true のあいだだけ毎フレーム描く。ほかの画面の描き方は変えていない。
- 状態ログ: レーダーを表示した分の stats 行に `anim=描いた回数/遅れた回数` を足した。前の回から 25ms を超えて間があいた回を「遅れた」と数え、内訳(tick、描画、転送と表示待ち)を `anim: 遅れ …` の行で残す(1 分に 10 件まで)。
- `miharashi png` は、航空機の画面を CPU 版と GLES 版、残光の短い案と長い案で書き出す。

### 見つけた不具合: キーボードを探す処理が描画を止めていた
- 最初の版を動かすと、線が 10 秒ごとに引っかかった。`anim: 遅れ` の行では、tick の中で 300〜530ms 止まっていた。
- 原因は、キーボードがつながっていないときに 10 秒ごとに入力デバイスを開き直す処理(`keys.reopen`)だった。`/dev/input/event*` のすべてを libseat 経由で開き直すので、毎回数百 ms かかっていた。
  - この処理は操作パネル(#32)と一緒に入った。写真画面でも同じように 10 秒ごとに止まっていたはずだが、写真画面は描き直しが少なく、目立たなかった。
  - 状態ログの `worst_frame` は描画と表示だけを測るので、この停止は 12 時間試験の数値に出ていない。
- 直し方: `/dev/input/event*` の一覧を前回と比べ、増減したときだけ開き直す(`Keys::reopen_if_changed`)。一覧を読むだけなので、デバイスは開かない。

| 単体テスト(offscreen) | 線の後ろ(残光)が緑、線の手前が暗い、円の外は背景のまま、線が通った直後の点がこれから通る点より明るいことを画素で確かめた |

## 重い描画のベンチマーク B1: コネクトーム(PR4)

将来載せたい「MaleCNS のシナプス反応の可視化」と同じ規模のグラフを GPU で描き、内蔵 GPU でどこまで描けるか、CPU と GPU をどれだけ使うかを測った。実データは読み込まず、規模だけを合わせた合成データを使う。

### 作ったもの
- `miharashi bench-gpu`(`crates/miharashi-app/src/gpu_bench.rs`)。表示カードの render node に surfaceless で描くので、表示中の miharashi を止めずに測れる(KMS には出さない)。
  - `miharashi bench-gpu [--size WxH] [--seconds N] [--fps N(0 = 上限)] [--neurons N] [--synapses N] [--stim N] [--gain X] [--lines none|all|active] [--out FILE.png]`
  - 1 秒ごとと最後に、fps、GPU の時間(伝播、描画)、命令を出す CPU の時間、自プロセスの CPU%、`gpu_busy_percent`、CPU パッケージの電力(RAPL)、発火しているニューロンの割合を出す。
- 合成データ(`miharashi-gpu` の `connectome.rs`、`synth`)
  - ニューロン 16 万個を、左右対称に置いた 48 個の塊(ニューロピル)に散らす。
  - 結合 300 万本のうち、85% は同じ塊の中、10% は反対側の対になる塊、5% はどこかのニューロンから引く。受け手 1 個あたりの本数は平均 19 本で、0.25〜1.75 倍にばらつかせた。乱数の種を固定しているので、毎回同じグラフになる。
- 発火の伝播(compute shader、毎フレーム)
  - 状態は (膜の値 v, 不応期 r)。入ってくる結合の送り手の v を合計し、`gain × 合計 × (1 − r)` を確率として発火する。発火したら v と r を 1 にし、発火しなければ v は 0.80 倍、r は 0.95 倍に減衰する。
  - 確率で発火させると、1 回の発火から次に何個が発火するか(分岐比)を `gain` で調整できる。`gain` = 0.012 で、発火しているニューロンが約 1.5% の状態で落ち着く(0.011 で 0.4%、0.015 で 5%、0.03 で 20%)。
  - CPU は、1 フレームに 4 個、刺激するニューロンの番号を渡すだけ。
- 描画(加算合成、カメラは y 軸の回りに 0.15 rad/秒で回る)
  - 点: ニューロン全部。発火したものは大きく、琥珀色に光る。
  - 線は 2 通り。
    - `all`: 300 万本を毎フレーム全部描く(力ずく。上限を測るため)。
    - `active`(既定): 配線の 16 本に 1 本(約 19 万本)を薄く描き、送り手が光っている(v > 0.1)結合だけを明るく描く。光っている結合は伝播の compute shader が集めて添字の列に書き、間接描画(`glDrawElementsIndirect`)で描く。CPU は本数を知らなくてよい。
- GPU の時間は `GL_EXT_disjoint_timer_query` で伝播と描画に分けて測る。毎フレーム fence を置き、2 フレーム前の完了を待つ(`glFinish` は使わない)。時計が飛んだ回(`GPU_DISJOINT`)の値は捨てる。
- 使えることを確かめた機能(このホスト): `GL_EXT_disjoint_timer_query` あり、頂点シェーダーの SSBO 16 個、SSBO の上限 3,913MB、compute のグループの大きさ 1,024。

### 確認したこと
| 項目 | 結果 |
|---|---|
| 単体テスト(合成データ) | 頼んだ数のニューロンと結合ができ、結合が受け手の順に並ぶ。同じ種なら同じグラフ |
| 単体テスト(offscreen) | 刺激したニューロンだけが発火し、数段で広がる。発火したところが明るく描ける |
| 単体テスト(カメラ) | 脳の中心が画面の中央に、左右の端(x = ±1.6)も画面に入る |

### 実機の計測(2026-10-15 00:20〜00:33、2560×1080、30fps 指定、release)
表示中の miharashi(状況画面)と同じ内蔵 GPU で動かした。データの転送は 10ms で、VRAM が 48MB → 55MB、GTT が 113MB → 178MB に増えた(VRAM は 64MB しかないので、ほとんどが GTT に置かれる)。

| 条件 | fps | GPU の時間 平均 / p95 [ms](伝播 + 描画) | GPU の埋まり具合 | CPU の時間/フレーム | `cpu_self` | 電力 |
|---|---:|---:|---:|---:|---:|---:|

| `active`、10 分 | **30.0** | 28.7 / 31.6(7.0 + 21.7) | 86% | 0.09ms | **1.0%** | 32.3W |

- `gpu_busy_percent` は、待たずに描き続ける条件ではタイマーと同じく 100% になった。30fps 指定の `active` では平均 22% で、タイマーの値(86%)と大きく違った。差の原因は確かめていない。

### 読み取れること
- **CPU は目標を大きく下回った。** どの条件でも `cpu_self` は 1% 前後で、命令を出す時間は 1 フレーム 0.1ms。伝播も、描く結合を選ぶのも GPU で済んでいて、CPU の仕事は規模によらない。計画の目標の案(B1 は 30fps 以上で `cpu_self` 5% 以下)は、`active` で満たした。
- **300 万本を毎フレーム全部描くのは、この内蔵 GPU では無理**(6.8fps)。描画の時間は線の本数にほぼ比例し、画素数を 1/4 にすると半分になる。重なった線を加算合成で塗る量(帯域)と、頂点の処理の両方で決まっている。
- **「光っている結合だけ描く」方式なら 30fps で描ける。** ただし GPU は 86% 埋まり、余裕が少ない。カメラの向きで描画の時間が変わるので、p95 は 31.6ms とフレームの間隔(33ms)に近い。
- **GPU を埋めると、表示側が遅れる。** `active` では表示の転送が 7ms から約 20ms に延びた(状況画面では見た目に分からない)。`all` では表示が約 0.5 秒止まった。表示と同じ GPU で重いエフェクトを描くなら、GPU の埋まり具合に上限を決める必要がある。
- 伝播は 1 フレーム約 7ms で、描く量によらずかかる(30fps で GPU の約 21%)。受け手ごとに送り手の値を読み集めるので、メモリを飛び飛びに読む量で決まる。結合の送り手だけの配列を別に持つようにして、待たずに描き続ける条件で 7.7ms から 6.0ms に減った(30fps 指定のときは約 7ms)。
- 電力は、ベンチなしより約 9W 増えた(パッケージ全体。CPU と内蔵 GPU は同じパッケージ)。解像度を半分にすると約 5W 増で済んだ。

### 将来のエフェクトの予算(案)
- 表示と同じ内蔵 GPU で描くので、**エフェクトに使う GPU の時間は 30fps で 1 フレーム 16ms(埋まり具合 50%)以下**を目安にする。残りを表示(60fps のレーダー画面など)に残す。
- MaleCNS 全体級(16 万 / 300 万本)なら、伝播は毎フレーム GPU で回し、線は「光っている結合 + 間引いた配線」を半分の解像度で描けば、この予算に収まる(1280×540 で 15.3ms、46%)。
  - 線の層だけを半分の解像度で描いて拡大して重ねる方法は、まだ作っていない。実際のエフェクトを作るときに入れる。
- CPU の予算はほぼ使わない(1% 前後)。CPU を空けるという PoC-005 の目的に合う。

## 重い描画のベンチマーク B2: 動画と検出枠(PR4)

将来載せたい「リアルタイム動画認識の状況表示」を想定して、1080p30 の H.264 を内蔵 GPU でデコードし、検出枠 50 個とラベルを重ねて描いた。認識そのものはしない(NVIDIA か gpu-eval 側で動かす想定)。検出枠は、画面の中を動き回る合成の枠で代わりにした。

### デコードの手段
計画では、PR4 の最初に cros-libva と ffmpeg(vaapi)を比べて決めることにしていた。2026-10-15 にユーザーと相談して、**ffmpeg** にした。

- ffmpeg は動画ファイルの読み込み(MP4 など)からデコードまでを受け持つ。将来のカメラやネットワーク配信の映像(RTSP)にも、そのまま使える。
- cros-libva は H.264 の解析を Rust で行うが、MP4 の読み込みは自分で書く必要がある。ライブラリはまだ若く、仕様がよく変わる。
- ビルドには `libavcodec-dev`、`libavformat-dev`、`libavutil-dev`、`libclang-dev`(bindgen 用)が要る。このホストには導入済み。実行時に使う `libavcodec61` などは、もともと入っている。

### 作ったもの
- 新しいクレート `crates/miharashi-video`(`ffmpeg-sys-next`、avcodec と avformat だけ)。
  - 動画を開き、表示カードの render node の VA-API でデコードする。ソフトウェアデコードには戻らない(VA-API が使えなければ開けない)。
  - デコードした 1 枚は、`av_hwframe_map` で DRM PRIME(dmabuf)に写して渡す。画素は GPU のメモリに置いたままで、CPU に読み出さない。このホストでは NV12 が Y(R8)と UV(GR88)の 2 枚に分かれて来る(修飾子は linear)。
  - 最後まで読んだら先頭に戻って繰り返す。
  - ffmpeg の開発用パッケージが無い環境でもビルドできるように、ワークスペースの既定のビルドには入れない(`default-members`)。`miharashi-app` の `video` 機能を有効にしたときだけ使う。
- `miharashi-gpu` の `video.rs`
  - dmabuf を EGLImage にして(`EGL_EXT_image_dma_buf_import`)、テクスチャに結びつける(`glEGLImageTargetTexture2DOES`)。
  - Y と UV をシェーダーで RGB にする(BT.709、限定範囲)。動画は縦横比を保って画面の中央に置く(2560×1080 なら左右に 320px ずつ空く。説明や入出力の表示に使う想定)。
  - 検出枠(辺の太さ 3px)とラベルはインスタンス描画で描く。ラベルの文字は、CPU で起動時に 1 回だけアトラスに描いておく。
  - EGLImage とデコーダーのサーフェスは、GPU が読み終えるまで(2 フレーム)持っておいてから返す。
- `miharashi bench-gpu --video FILE [--detections N] [--size WxH] [--seconds N] [--fps N] [--out FILE.png]`(`cargo build --release --features miharashi-app/video` でビルドしたときだけ)。
  - 1 秒ごとと最後に次の値を出す。
    - GPU の時間: 動画を描く分と、枠とラベルを重ねる分。
    - デコーダーから 1 枚受け取るまでの時間と、テクスチャに結びつけるまでの時間。
    - CPU の時間、`cpu_self`、`gpu_busy_percent`、電力。

### 確認したこと
| 項目 | 結果 |
|---|---|
| 単体テスト(デコード) | 320×240 の H.264 を VA-API でデコードし、Y(R8)と UV(GR88、160×120)の 2 枚の dmabuf で受け取れる。最後まで読むと先頭に戻る |
| 単体テスト(検出枠) | 動き回る枠が動画の外に出ない |
| 画像で確認 | 試験動画(ffmpeg の testsrc2)の色帯の色が正しく、枠とラベルの位置が合っている |
| ffmpeg のコマンドで比較(60 秒の 1080p30) | VA-API は 2.6 秒でデコードし、CPU は 0.24 秒。CPU だけ(1 スレッド)だと 4.5 秒 |

### 実機の計測(2026-10-15 01:01〜01:14、2560×1080、動画のフレームレート 30fps に合わせる、release)
試験動画は ffmpeg で作った 1080p30 の H.264 を 2 本使った。

| 動画 | 時間 | fps | GPU の時間 平均 / p95 [ms](動画 + 重ね) | GPU の埋まり具合 | デコード待ち 平均 / p95 | 取り込み | `cpu_self` |
|---|---|---:|---:|---:|---:|---:|---:|
| testsrc2、8Mbps | 10 分 | **30.0** | 1.25 / 1.44(1.17 + 0.08) | 4% | 0.59 / 1.80 ms | 0.05 ms | **2.1%** |
| testsrc2 にノイズ、12Mbps(デコードが重い) | 2 分 | 30.0 | 1.28 / 1.46(1.18 + 0.10) | 4% | 0.75 / 1.53 ms | 0.06 ms | 2.6% |

- GPU の時間はシェーダーで描く分だけで、動画のデコード(VCN)の時間は入っていない。VCN の使用率は測っていない。
- 8 秒の試運転では `cpu_self` が 1.25% だった。本計測で 2.1% に上がったのは、計測中に別の処理(NVIDIA GPU の `llama-server`)が動いていて、システムの負荷(load average 8)が高かったためとみられるが、確かめていない。
- **電力は比べられなかった。** 計測中ずっと、別の処理が NVIDIA GPU を使っていた(使用率 0〜93%)。待機時の値も 46.6W と、B1 のとき(23.6W)の倍になっていた。
- NVIDIA GPU を使っていたのは `llama-server` だけで、ベンチマークのプロセスは使っていない(`nvidia-smi --query-compute-apps`)。
- 表示中の miharashi(状況画面)の `present_ms` は、平均 6.5〜8.8ms、p95 11〜20ms で、ベンチなしのとき(平均 7ms)と変わらなかった。

### 読み取れること
- **1080p30 の動画と検出枠 50 個は、内蔵 GPU で軽く描ける。** GPU の埋まり具合は 4% で、B1(半分の解像度で 46%)と比べてずっと小さい。デコードは VCN が受け持つので、描画の GPU の時間をほとんど使わない。
- **CPU は目標の案(30fps で `cpu_self` 10% 以下)を大きく下回った**(2.1%)。CPU の仕事は、デコーダーに次の 1 枚を頼んで受け取ること(0.6ms)と、dmabuf をテクスチャに結びつけること(0.05ms)だけ。画素はコピーしていない。
- ノイズを入れてビットレートを上げても、デコード待ちが 0.6ms から 0.75ms に延びただけだった。
- 表示側への影響は見えなかった。
- コネクトーム(B1、46%)と同じ画面に並べると、合わせて約 50% で、予算の上限ちょうどになる。両方を同時に出すなら、どちらかを軽くする必要がある。
