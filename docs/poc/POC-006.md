# PoC-006 VRM 描画の単体スパイク(Issue #71 A)

目的: 内蔵 GPU(Ryzen 7 9700X の Radeon、2 CU)で、VRM 1.0 モデルを GLES 3.2 でどのくらいの速さで描けるかを、画面に組み込む前に測る。本Issue: [#71](https://github.com/ysogabe/miharashi/issues/71)(「計画の見直し」の A)。画面への表示・画面切替(B)は #74 の後で、ここでは扱わない。

> **この文書の読み方**: 「計測結果(合成モデル)」はコードから組み立てた VRM 1.0 での結果、「実モデルでの計測(AI ニケちゃん)」は実際の VRM 1.0 での結果。数値だけを載せ、画像は載せない。

## 作ったもの

- `crates/miharashi-vrm`(新クレート。`miharashi-app` には依存しない)
  - ライブラリ部の依存は `glow`(0.18)・`gltf`(1.4)・`serde_json`・`image`(テクスチャのデコードと PNG 保存)。`miharashi-gpu`(と `libc`)は feature `bench`(既定で有効)の任意の依存で、使うのは計測用の bin(`required-features = ["bench"]`)だけ。GPU の試験は dev-dependencies の `miharashi-gpu` を使う。ライブラリとして使うだけなら `default-features = false` で外せる。
  - 読み込みでは、属性の accessor の型(POSITION/NORMAL は VEC3 f32、TEXCOORD_0 は VEC2 の f32 か正規化整数、JOINTS_0/WEIGHTS_0 は VEC4、indices はスカラー、morph target の POSITION/NORMAL は VEC3 f32)と数(POSITION と同じ)を読む前に確かめ、合わなければエラーにする(gltf クレートの assert による panic を避ける)。ノードを辿るときは再訪(children の循環・親が複数)をエラーにする。bufferView も sparse もない accessor(仕様では「すべて 0」。UniVRM が変化のない morph target に出す)は、0 を詰めた bufferView を足して読む。16 ビットのテクスチャは上位 8 ビットだけを使う。
  - `Renderer::new` が途中で失敗したときは、作った GL オブジェクトを消してから返る。
  - `model`: glb の読み込み。ノードの変換とスキニング(バインドポーズ)を頂点に焼き込み、静止ポーズとして持つ。
  - `vrm`: `VRMC_vrm` を自前で読む(`specVersion` の確認と、expressions のプリセット/カスタム名 → morph target bind の対応だけ)。VRM 0.x(拡張 `VRM`)は「未対応」のエラーにする。
  - `render`: GLES での描画。Lambert の平行光源、baseColor テクスチャ(SRGB8_ALPHA8、ミップマップ)、深度テスト、OPAQUE / MASK(discard)/ BLEND(描画順の整列なし、深度書き込みなし)。カメラはバインドポーズの外接箱から、全身が収まる距離に自動で置く(+Z から -Z を見る)。
  - 表情: expression の weight から morph target を CPU で合成し、頂点バッファを `glBufferSubData` で更新する。`destroy(gl)` で GPU リソースをすべて解放する。
  - `synth`: 試験・計測用の合成 VRM 1.0(頭 = テクスチャ + morph target `blink`、胴、スキン付き三角形)。
- `vrm-bench`(`crates/miharashi-vrm/src/bin/vrm-bench.rs`): `Offscreen::with_fbo`(EGL surfaceless + FBO)に描いて計測する。`with_fbo` の FBO には深度がないので、クロージャの中で深度 renderbuffer(DEPTH24_STENCIL8)を付けて、終わったら外して消す(`miharashi-gpu` は変えていない)。

`vrm-runtime` / `vrm-spec` / `serde_vrm` は採用していない。Issue にある「比較して採否を記録する」は**まだ実施していない**(自前の解釈は expressions だけで足りたので、先に計測を進めた)。B に進む前に、保守状況・ライセンス・GPU 非依存性を確かめて追記する。

## 動かし方

VRM モデルはリポジトリに置かない。各自で**利用条件(再配布・商用・表示形態)を確認して**用意する。

```sh
cargo build --release
# 合成モデル(モデルの用意が要らない)
./target/release/vrm-bench --synthetic --size 1280x720 --frames 600 --png /tmp/vrm.png
# 実モデル
./target/release/vrm-bench --model /path/to/model.vrm --size 1920x1080 --pci 0000:10:00.0 --png /tmp/vrm.png
```

| 引数 | 内容 |
|---|---|
| `--model <path.vrm>` / `--synthetic` | 読み込むモデル / 合成モデル(`--segments` で三角形数、`--texture` でテクスチャの 1 辺) |
| `--pci` | 描く GPU の PCI アドレス(既定 `0000:10:00.0` = 内蔵。NVIDIA は `0000:01:00.0`) |
| `--size` | `1280x720`(既定)、`1920x1080` など |
| `--frames` | 計測するフレーム数(既定 600、そのほかに 5 フレームのウォームアップ) |
| `--seconds` | 指定すると、フレーム数ではなくこの秒数だけ描き続ける |
| `--fps` | 指定すると、各フレームのあと次のフレームの時刻まで sleep して間隔を保つ(例 30)。`--seconds` と組み合わせて、一定 fps での CPU 使用率を測る |
| `--expression` | 動かす expression(省略時は `blink` → `happy` → `aa` → morph のある最初のもの) |
| `--still` | weight を 1 に固定する(省略時は 2 秒周期で 0 → 1 → 0) |
| `--png` | 最後のフレームを PNG に保存(見た目の確認用) |

出力: `GL_RENDERER` / `GL_VERSION`(llvmpipe でないことの確認)、モデルの規模(メッシュ・三角形・テクスチャ・morph target)、初期ロード時間(ファイル読み込み + 解釈 / GPU 転送)、フレーム時間の平均と p95(毎フレーム `glFinish` で GPU の完了まで待つ)、morph の CPU 時間、プロセスの CPU 使用率(`getrusage`)、GPU メモリ(`mem_info_vram_used` と `mem_info_gtt_used`)。

## 確認したこと

| 項目 | 結果 |
|---|---|
| 内蔵 GPU で描けている(ソフトウェアレンダリングではない) | `GL_RENDERER` = AMD Radeon Graphics (radeonsi, raphael_mendocino, LLVM 19.1.7, DRM 3.61, 6.12.111)、`GL_VERSION` = OpenGL ES 3.2 Mesa 25.0.7(llvmpipe ではない) |
| 見た目 | PNG で、テクスチャ付きの頭・胴・スキン付き三角形が正しい向きと位置に描けていることを確認(合成モデル) |
| ノード変換・スキニング | 試験で、親ノードの移動と、関節の移動(スキンの三角形)が頂点に効いていることを確認 |
| 表情 | 試験で、`blink` の weight で頂点が動くこと、存在しない expression がエラーになることを確認 |
| VRM 0.x | 「未対応」のエラーになる |
| 解放 | 描画後に `destroy` と深度 renderbuffer の削除を呼び、GL エラーが出ない |

## 計測結果(合成モデル、2026-10-18、release ビルド、各 600 フレーム)

| モデル | 解像度 | フレーム平均 / p95 | morph の CPU | プロセス CPU | ロード(ファイル+解釈 / GPU 転送) |
|---|---|---|---|---|---|
| 4,609 三角形、テクスチャ 1024² | 1280×720 | 0.07 / 0.08 ms | 0.004 ms | 52.7% | 5 ms / 8 ms |
| 320,001 三角形、テクスチャ 4096² | 1280×720 | 0.52 / 0.55 ms | 0.265 ms | 57.0% | 81 ms / 36 ms |
| 320,001 三角形、テクスチャ 4096² | 1920×1080 | 0.59 / 0.61 ms | 0.263 ms | 50.9% | 82 ms / 19 ms |

GPU メモリ(2 行目、`gtt` は描画前 139MB → 描画後 385MB、`vram` は 55MB のまま変化なし)。内蔵 GPU は GTT(システムメモリ)に載るので、約 246MB 増えた(転送した頂点・インデックス・テクスチャ約 93MB より多い。ドライバの確保単位や、`generate_mipmap`、深度バッファなどが含まれると考えられるが、内訳は未確認)。`destroy` 後も GTT がすぐには戻らない(プロセスが生きているあいだは Mesa が確保を持ち続ける)ので、解放の確認は GL エラーなしと、プロセス終了後の値で行う必要がある(後者は未確認)。

### 読み取れること

- 合成モデルでは、32 万三角形・4096² のテクスチャでも 1 フレーム 0.6 ms 前後で、720p / 1080p のどちらも 30fps(33 ms)の目標に対して大きな余裕がある。ただし球だけで構成した単純な形で、頂点は大半が小さく、**実モデルの重さ(髪・服の多層、BLEND の重なり、スキン、MToon)を代表しない**。実モデルの数値が出るまで、達成・未達の判断はしない。
- 1080p でもフレーム時間がほぼ増えない(0.52 → 0.59 ms)ので、この負荷では画素ではなく頂点側が支配的。
- morph の CPU 合成は 32 万頂点で 0.27 ms/フレーム。実モデルで morph を持つのは顔のメッシュ(数千〜数万頂点)だけなので、CPU 合成で足りる見込みだが、これも実モデルで確認する。
- **プロセス CPU 使用率の 50〜57% は、そのまま PoC-005 の目安に使えない**。この bench は `glFinish` を毎フレーム呼んで連続で描くので、待ちの間のドライバの CPU 消費を含み、計測時間も 0.3〜0.4 秒と短い。30fps に制限して一定時間走らせる計測は、下の「実モデルでの計測」で実施した(`--fps 30 --seconds 30`)。

## 実モデルでの計測(AI ニケちゃん、2026-10-18、release ビルド、内蔵 GPU)

- モデル: AI ニケちゃん `nikechan_v2.vrm`(tegnike/aituber-kit の `public/vrm/nikechan_v2.vrm`、元は tegnike/nikechan-assets の公式素材。非営利の個人利用・AI への入力は許可、**再配布・同梱は禁止**)。**AI ニケちゃん(非公式ファンメイドとしての技術検証)であり、モデルはリポジトリに同梱しない**(`.gitignore` に `*.vrm` を足した)。
- 取得手順(リポジトリの外に置く):
  ```sh
  mkdir -p ~/.cache/miharashi/vrm
  curl -fL -o ~/.cache/miharashi/vrm/nikechan_v2.vrm \
    https://github.com/tegnike/aituber-kit/raw/main/public/vrm/nikechan_v2.vrm
  ./target/release/vrm-bench --model ~/.cache/miharashi/vrm/nikechan_v2.vrm --png /tmp/nikechan.png
  ```
- 規模: VRM 1.0、メッシュ 4、プリミティブ 14、頂点 81,647、三角形 141,746、マテリアル 13、morph target 58、テクスチャ 16 枚(256×512 が 1、512² が 13、1024² と 2048² が各 1)、ファイル 約 23MB。expression は 29 個が morph bind を持つ(aa / blink / happy / lookDown など)。
- ロード: ファイル読み込み + 解釈 61〜63 ms、GPU 転送 10〜12 ms(転送 47MB)。
- 初回は読み込みが 2 か所で失敗し、直した(合成モデルでは出なかった形): ①bufferView のない accessor(変化のない morph target の「すべて 0」)、②16 ビット(R16G16B16A16)のテクスチャ。

| 解像度 | 条件 | フレーム平均 / p95 | morph の CPU | プロセス CPU |
|---|---|---|---|---|
| 1280×720 | `--frames 600`(連続描画) | 0.29 / 0.31 ms | 0.062 ms | 32.2%(cpu 0.06 s / wall 0.18 s) |
| 1920×1080 | `--frames 600`(連続描画) | 0.38 / 0.39 ms | 0.063 ms | 25.7%(cpu 0.06 s / wall 0.23 s) |
| 1280×720 | `--fps 30 --seconds 30`(900 フレーム) | 1.87 / 2.20 ms | 0.133 ms | **1.2%**(cpu 0.36 s / wall 30.00 s) |

- GPU メモリ(1280×720): `gtt` は描画前 139MB → 描画中 291MB(1920×1080 は 302MB)、`vram` は 55MB のまま。
- 30fps に制限した 30 秒で、プロセスの CPU 使用率は 1.2%(`glFinish` の待ちを含む。表情の weight を 2 秒周期で動かして morph の合成・転送もしている)。連続描画の 25〜32% は計測時間が 0.2 秒と短く、待ちの間のドライバの CPU 消費を含むので目安にしない。
- 30fps 制限ではフレーム時間が連続描画(0.29 ms)より長い(1.87 ms)のは、GPU が間隔の空いた負荷では低いクロックに落ちるためと考えられる(未確認)。どちらも 33 ms の予算の 6% 以下。
- 見た目(1280×720 の PNG を目で確認): 正面を向いた T ポーズの全身が、画面中央に縦いっぱい(余白は左右)で描けている。顔・髪(紫)・T シャツ(「AITuber」の文字)・ショートパンツ・靴まで、**テクスチャが乗っていて、欠けている部位や裏返しの面はない**。髪はバインドポーズのまま(揺れなし)、目や肌の陰影は Lambert のみで MToon の輪郭線・リムライトはない(AITuberKit とは見た目が違う)。
- GPU 使用率(`gpu_busy_percent`)は測っていない。

## 未対応(今回の範囲外)

> 以下は焼き込み時点(上の計測)のもの。スキニング・MToon・SpringBone・humanoid は、末尾の「見た目を AITuberKit に近づける」で対応した。

- **スキニング(アニメーション)**: バインドポーズの 1 回だけ頂点に焼き込む。ボーンを動かしての変形(CPU か GPU か)は未実施。
- **MToon**: 使わない。`VRMC_materials_mtoon` は読まず、Lambert + baseColor のみ(見た目は AITuberKit とは違う)。
- **SpringBone**(髪・服の揺れ)、**LookAt**(視線)、**humanoid**: 読まない。
- **VRM 0.x**: エラーにする(拡張 `VRM`)。0.x と 1.0 の互換性は別に検証する。
- そのほか: baseColor 以外のテクスチャ(法線・emissive)、`KHR_texture_transform` などの拡張、頂点カラー、`TEXCOORD_1`、モデルの表示サイズ・向きの個別調整、画面への組み込み。

## 実モニターでの表示(vrm-view)

`vrm-bench` は画面に出さないので、実際のモニター(DRM/KMS)に出して見た目と負荷を確かめる bin を足した(`crates/miharashi-vrm/src/bin/vrm-view.rs`、feature `view`。既定で有効)。#74 の「画面に GL を貸す口」の下調べを兼ねる。

- `miharashi-gpu::GlesDisplay` に 2 つ足した。`with_gl(f)` は既定の framebuffer を bind して GL を `f` に貸すだけ(初期化と後始末用)、`present_with(f)` は `with_gl` で描かせたあと swap → page flip の完了待ちまで行う。`present_frame` と `present_with` の swap 以降は同じ private 関数(`flip`)で、`present_frame` の挙動は変えていない。
- 既定の framebuffer(EGL のウィンドウ surface)には深度がないので、vrm-view が RGBA8 の renderbuffer + `DEPTH24_STENCIL8` の FBO を 1 つ作って使い回し、毎フレーム `blit_framebuffer` で画面へ写す。終了時に FBO を消し、`Renderer::destroy` のあとで `GlesDisplay` を drop する(Drop で元の CRTC に戻る)。`egl.rs` の config は変えていない。
- 表示先は `drm_select::scan` → `choose_card` → `choose_connector` で決め、カードを直接 open する(libseat は使わない)。そのため **キオスク(miharashi.service)を止めてから**実行する。
- 演出(`demo` モジュール、GL に触れない): 表情の weight は blink なら 4 秒おきに 0.3 秒だけ閉じる(それ以外の表情は 4 秒周期で 0 → 1 → 0)。カメラはモデルの中心のまわりを ±20 度、16 秒周期で往復する。背景は暗い色。
- カメラは高さ基準で置く(`render::view_proj`)。2560x1080 の横長でも全身が縦に収まり、±20 度振っても横にはみ出さないことを単体テストで確認している(回すと幅が奥行きぶん増えるので、幅は水平の対角で見積もる。`Renderer::render` の距離の式もこれに揃えたので、正面でも 4:3 より狭い画面では以前よりわずかに引く)。

```sh
sudo systemctl stop miharashi
./target/release/vrm-view --model ~/.cache/miharashi/vrm/nikechan_v2.vrm --seconds 60
sudo systemctl start miharashi
```

| 引数 | 内容 |
|---|---|
| `--model <path.vrm>` / `--synthetic` | 読み込むモデル / 合成モデル |
| `--card` | 表示するカード(既定 `driver:amdgpu`。`pci:0000:10:00.0`、`/dev/dri/card1`、`auto` も可) |
| `--connector` | コネクター名(既定 `auto`) |
| `--mode` | `preferred`(既定)か `2560x1080` など |
| `--seconds` | 描き続ける秒数(既定 60。経過したら終了。SIGINT/SIGTERM でも正常終了する) |
| `--expression` | 動かす表情(既定 `blink`) |

起動時に標準エラーへモデルの規模、表示先、表示モード、`GL_RENDERER` を出し、5 秒ごとに fps・フレーム時間の平均(vsync の待ちを含む)・プロセスの CPU% を出す。

**注意**: キオスクを止めている間は、画面が使えない(表示も操作パネルの表示も止まる)。実行が終わったら必ず `sudo systemctl start miharashi` で戻す。DRM master を取り合うので、キオスクが動いたまま実行しない。

### 実モニターでの計測値

2026-10-18、card0(amdgpu 0000:10:00.0)の HDMI-A-1、2560x1080@60Hz、`nikechan_v2.vrm`、90 秒。

- 60.0fps を維持(フレーム時間 16.67ms、vsync 待ち)。プロセスの CPU は 1.0〜1.6%。5397 フレームで正常終了し、キオスクへの復帰も確認した。見た目に問題なし(ユーザー確認)。
- 内蔵 GPU の負荷(sysfs を 0.2 秒ごとに採取、45 秒):

| 状態 | busy 平均 | sclk 平均 | VRAM / GTT | CPU |
|---|---|---|---|---|
| 停止中 | 0.0% | 600MHz | 23MB / 13MB | — |
| キオスク(状況画面) | 0.7% | 611MHz | 52MB / 144MB | — |
| vrm-view | 15.2% | 865MHz(最大 2200) | 43MB / 164MB | 1.0〜1.8% |

- 見方: busy の p95 が 99% と出るのは、毎フレーム短時間だけ全力で描くため。平均で見る。約 15% は 16.7ms のうち約 2.5ms の描画に当たる。30fps にすればおよそ半分の見込み。MToon(輪郭線)・GPU スキニング・SpringBone を入れると増える。

## 未対応・次の手順(B の前に直す)

読み込みの防御は、確かめられる範囲で入れた(上の「作ったもの」)。残りは次のとおり。

- accessor の型は、KHR_mesh_quantization のような整数の POSITION / NORMAL(i8・i16)を**未対応(エラー)**として弾いているだけで、読む対応はしていない。TEXCOORD_0 の整数は正規化のときだけ読む。
- sparse の accessor は gltf クレートに任せている。範囲外の sparse index を持つ壊れた glb での挙動は未確認。
- `JOINTS_1` / `WEIGHTS_1`(5 本以上の関節)、`TEXCOORD_1`、頂点カラーは読まない(JOINTS_0 の 4 本まで)。
- テクスチャは 1 枚が 2048² でも読めたが、巨大な画像(幅 × 高さが非常に大きい)を弾く上限は設けていない。
- 実モデルは 1 つ(ニケちゃん)だけ。ほかの VRM 1.0(別のツールで出したもの)での確認は B の前に増やす。

## 次の手順

1. 実モデルで足りない見た目(MToon の簡易版、法線・emissive)を検討する。
2. GPU の使用率(`gpu_busy_percent`)を測り、PoC-005 の目安値を決める(CPU 使用率は 30fps で測定済み)。
3. `vrm-runtime` などとの比較結果を記録する。
4. ボーンの簡単な変形(CPU スキニング)のコストを測る。
5. #74 の「画面に GL を貸す口」が決まったら、`miharashi-app` 側に `Screen` を実装する薄い部分を足す(B)。

## 見た目を AITuberKit に近づける(2026-10-18、ブランチ `poc/vrm-mtoon-pose`)

目的は、内蔵 GPU(9700X の radeonsi)で、AITuberKit(three-vrm)に近い見た目がどこまで出せて、負荷がどれくらいかを把握すること。モデルは AI ニケちゃん(`nikechan_v2.vrm`、画像はリポジトリに載せない)。実モニター(vrm-view)での実行は未実施(親が行う)。

### 段階ごとの到達度

| 段階 | 内容 | 到達度 |
|---|---|---|
| 1 実行時スキニング | 焼き込みをやめ、ノード階層(ローカル TRS)を毎フレーム評価 → 関節行列を UBO(`mat4[256]`、std140)で渡して頂点シェーダでスキニング | できた |
| 2 自然なポーズ | humanoid(`humanBones`)から上腕・前腕を引き、T ポーズから腕を下ろす | できた(手指は T ポーズのまま) |
| 3 待機アニメーション | 呼吸(胸・背骨の回転、腰の上下 2mm)、首・頭の揺れ、まばたき(既存の demo) | できた |
| 4 MToon 近似 | shade 色/テクスチャ、toony/shift の 2 階調、parametricRim、emissive、輪郭線(world/screen、色、lightingMix、幅テクスチャ) | 一部(MatCap・法線・emissive テクスチャ・UV アニメ・shadingShift テクスチャは未対応) |
| 5 SpringBone | stiffness/gravity/drag/hitRadius、球とカプセルのコライダー、three-vrm と同じ Verlet | できた(center なし、見た目の確認は静止画のみ) |

- **段階 1 の実装**: 頂点はメッシュのローカル空間のまま持つ(morph の差分もローカル)。スキンなしのプリミティブは「自分のノード 1 つだけの関節」として同じ経路に乗せる。JOINTS_0/WEIGHTS_0 は morph で書き換えない別の頂点バッファ(u16×4 + f32×4)。法線は `mat3(skin)`(関節は剛体とみなす)。関節は ニケちゃん 177 個(1 スキンを 4 メッシュで共有)、UBO は 16KB(mat4 が 256 個まで。GLES 3.0 が保証する下限)を使い、超えると読み込み時にエラー。初期姿勢の外接箱は CPU で同じ計算をして求める。
  - 確認: 焼き込み版(段階 1 の前の HEAD)と同じ条件の 2560x1080 の PNG を画素で比べ、最大差 16/255(脚の法線の丸め差)で、輪郭・陰影とも一致。
- **段階 2 の実装**: 骨のローカル軸は並びが決まっていない(ニケちゃんは根が 180° 回っていて肩のローカル回転も大きい)ので、ローカルで「70°」とは言わず、**ワールド空間の回転**を `local' = conj(P)·D·P·local`(P = 親のワールド回転)で掛ける(`anim::apply_world_rotation`)。上腕は「上腕→前腕」の向きを、真下から外へ 20°(`ARM_LEAN_DEG`)開いた向きに合わせる回転(= T ポーズから約 70° 下げる)。前腕は前(+Z)へ 18°(`ELBOW_BEND_DEG`)曲げる。待機モーションも同じ関数で骨に重ねる。
- **段階 4 の実装**: 光は正面上からの平行光源 1 つ(強さ 0.9)+ 環境光 0.1。`shading = linearstep(-1 + toony, 1 - toony, dot(N, L) + shift)`、色 = `mix(shade, lit, shading)`。`KHR_materials_unlit` は MToon があれば無視する。輪郭線は inverted hull(スキン後の法線方向へ押し出した裏面。world は m、screen は画面の高さに対する割合)。不透明/MASK → 輪郭線 → BLEND(renderQueueOffsetNumber の順)で描く。
- **段階 5 の実装**: 髪 55 本(各 2 関節)、コライダー 31(球)。ポーズ評価 → spring(骨ごとに Verlet と衝突、ローカル回転を決めて子のワールドを更新)→ 全体を再評価 → 関節行列。dt は 1/20 秒で打ち切り。最初のフレームは今の姿勢の尾の位置で止める。

### 見た目の所見(2560x1080 の PNG を目で確認)

- 段階 1(skin): 焼き込み版と同じ T ポーズ。まばたき(blink)も効く。
- 段階 2(pose): 腕が体側へ下り、前腕が少し前に曲がった自然な立ち姿。肩・脇の変形に破れはない。腕の開き 20° は、体からやや離れて見える(AITuberKit の標準の待機ポーズよりわずかに広い)。手指は伸びたまま。
- 段階 4(mtoon): 影が 2 階調になる(袖の下・髪の内側・首の下)が、正面上からの光なので、顔・Tシャツの正面はほぼ全面が明部で、2 階調は目立たない。肌・目の周りは明るく白っぽく見える(テクスチャの色のまま出している)。**ニケちゃんは全マテリアルでリム色・emissive が 0、MatCap なし**なので、リムと emissive は ニケちゃんの絵には出ない(合成モデルの GPU 試験で、リム・emissive・輪郭線が効くことは確認)。
- 輪郭線: ニケちゃんの `outlineWidthFactor` は 0.0005(0.5mm、worldCoordinates)。全身が 1080px に収まる大きさでは 1px 未満なので、**途切れた点線のようにしか出ない**(MSAA なしで、ジャギーも出る)。`--outline-scale 6` にすると 3mm 相当で、髪・顔・服・ショートパンツの縁が黒い線で出る(仕組みは動いている)。AITuberKit でも幅の指定は同じなので、同程度の細さのはず(三者の比較は未確認)。
- 段階 5(spring): 髪(ポニーテール・横髪)は崩れず、頭の揺れについて少しずれる。静止画では小さな差(約 3,400 画素)で、揺れの自然さは動画では未確認。

### 計測(release、内蔵 GPU、`nikechan_v2.vrm`、1200 フレームの連続描画)

GPU = 描画コマンドの発行 〜 `glFinish` の完了(ms の平均)。CPU = 1 フレームあたりの CPU 処理の平均(ms)。pose = ノード階層の評価 + 関節行列 + UBO 転送、morph = 表情の合成 + 頂点転送。`bake` は morph なし(表情が動かない)ので、morph が 0。

| 段階 | 解像度 | GPU ms | CPU pose ms | CPU spring ms | CPU morph ms |
|---|---|---|---|---|---|
| bake(焼き込み + Lambert) | 2560x1080 | 0.32 | 0 | 0 | 0 |
| skin(GPU スキニング + Lambert) | 2560x1080 | 0.58 | 0.004 | 0 | 0.062 |
| pose(+ ポーズ・待機) | 2560x1080 | 0.57 | 0.004 | 0 | 0.061 |
| mtoon(+ MToon・輪郭線) | 2560x1080 | 1.00 | 0.005 | 0 | 0.064 |
| spring(+ SpringBone) | 2560x1080 | 1.01 | 0.007 | 0.020 | 0.061 |
| bake | 1280x720 | 0.24 | 0 | 0 | 0 |
| skin | 1280x720 | 0.49 | 0.004 | 0 | 0.061 |
| pose | 1280x720 | 0.49 | 0.004 | 0 | 0.061 |
| mtoon | 1280x720 | 0.86 | 0.004 | 0 | 0.063 |
| spring | 1280x720 | 0.85 | 0.007 | 0.019 | 0.061 |

30fps に制限して 12 秒(`--fps 30 --seconds 12`)のときの GPU ms とプロセスの CPU 使用率(`glFinish` の待ちを含む):

| 段階 | 解像度 | GPU ms | プロセス CPU |
|---|---|---|---|
| bake | 2560x1080 | 1.86 | 0.8% |
| skin | 2560x1080 | 2.32 | 1.1% |
| spring | 2560x1080 | 2.97 | 1.6% |
| bake | 1280x720 | 1.60 | 0.7% |
| skin | 1280x720 | 2.23 | 1.1% |
| spring | 1280x720 | 2.72 | 1.5% |

- 連続描画の GPU 時間は、最大の `spring` でも 2560x1080 で約 1.0ms。60fps の予算(16.7ms)の約 6%、30fps の予算(33ms)の約 3%。GPU が低クロックになる間隔の空いた描画(30fps)では約 3ms(予算の 9%)。以前の実モニターの値(焼き込み、60fps で busy 約 15%)から、MToon・スキニングでおよそ 2〜3 倍に増えると見込む(実モニターでは未計測)。
- 増えた内訳は、GPU スキニングで +0.25ms(0.32 → 0.58)、MToon + 輪郭線で +0.43ms(0.57 → 1.00)。解像度を 1280x720 に下げても MToon 段階の差は小さい(1.00 → 0.86)ので、画素より頂点(14 万三角形 + 輪郭線の再描画)が支配的。
- CPU は、ポーズ評価が 5〜7µs、SpringBone が約 20µs、morph が約 60µs で、合計 0.1ms 未満。30fps でのプロセス CPU は 1.6%(PoC-005 の目安に十分収まる)。SpringBone を入れても CPU は問題にならない。

### AITuberKit との残りの差

- MToon: MatCap、法線マップ、emissive テクスチャ、shadingShift テクスチャ、UV アニメーション、`KHR_texture_transform`(ニケちゃんは単位)は未対応。GI(giEqualizationFactor)は定数の環境光で代用。リムはニケちゃんでは 0 で、実際のモデルでの見た目の確認はしていない。
- 光と色: AITuberKit の光の向き・強さ・トーンマップは未確認で、数値は目で合わせた近似(明るく白っぽく出がち)。シャドウマップ(影の落ち)なし。
- 輪郭線: MSAA なしで、細い線が途切れる。AITuberKit の画面ピクセル比・アンチエイリアスとの比較は未実施。
- ポーズ: 手指の曲げなし、視線(LookAt)なし、足の配置は T ポーズのまま。待機は呼吸と頭の揺れだけ(体重移動・腕の揺れなし)。
- 透明: BLEND は材質の順で描くだけ(カメラ距離による整列なし)。
- SpringBone: center なし、`gravityDir` は joint 単位のまま(three-vrm と同じ)、揺れの自然さは動画で未確認。コライダーは球とカプセルだけ(拡張の形は未対応)。
- 表情の morph は CPU 合成のまま(約 0.06ms。GPU morph に移す理由は今のところない)。
- 実モニターでの負荷(GPU busy・消費電力)は未計測。

### 次にやるなら

1. 親が vrm-view(下)で実モニターに出し、見た目(特に腕の角度 20° と輪郭線の細さ)と GPU の busy を測る。
2. 光の向き・強さ・ガンマを AITuberKit と並べて合わせる(明るさ・肌の白さ)。輪郭線は、MSAA か、ポストでのアンチエイリアスを検討する。
3. 指の軽い曲げ、体重移動などの待機を足す。
4. SpringBone を動画で確認し、揺れの強さ(stiffness)を必要なら調整する。

```sh
# 30fps、全部入り(spring)。キオスクは止めてから
sudo systemctl stop miharashi
./target/release/vrm-view --model ~/.cache/miharashi/vrm/nikechan_v2.vrm --fps 30 --seconds 60
# vsync(60fps)
./target/release/vrm-view --model ~/.cache/miharashi/vrm/nikechan_v2.vrm --seconds 60
# 段階の切り替え(bake / skin / pose / mtoon / spring)と輪郭線の確認
./target/release/vrm-view --model ~/.cache/miharashi/vrm/nikechan_v2.vrm --fps 30 --feature-level mtoon --outline-scale 6 --seconds 60
sudo systemctl start miharashi
```

`vrm-bench` / `vrm-view` の追加引数: `--feature-level bake|skin|pose|mtoon|spring`(既定 spring)、`--outline-scale <倍率>`(輪郭線の太さの倍率、確認用)、vrm-view の `--fps <N>`(既定は vsync)。vrm-bench は pose / spring / morph の CPU 時間と GPU ms を分けて出す。
