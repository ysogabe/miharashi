# PoC-006 VRM 描画の単体スパイク(Issue #71 A)

目的: 内蔵 GPU(Ryzen 7 9700X の Radeon、2 CU)で、VRM 1.0 モデルを GLES 3.2 でどのくらいの速さで描けるかを、画面に組み込む前に測る。本Issue: [#71](https://github.com/ysogabe/miharashi/issues/71)(「計画の見直し」の A)。画面への表示・画面切替(B)は #74 の後で、ここでは扱わない。

> **この文書の読み方**: 「計測結果(合成モデル)」はコードから組み立てた VRM 1.0 での結果、「実モデルでの計測(AI ニケちゃん)」は実際の VRM 1.0 での結果。数値だけを載せ、画像は載せない。

## 作ったもの

- `crates/miharashi-vrm`(新クレート。`miharashi-app` には依存しない)
  - ライブラリ部の依存は `glow`(0.18)・`gltf`(1.4)・`serde_json`・`image`(テクスチャのデコードと PNG 保存)。`miharashi-gpu`(と `libc`)は feature `bench`(既定で有効)の任意の依存で、使うのは計測用の bin(`required-features = ["bench"]`)だけ。GPU の試験は dev-dependencies の `miharashi-gpu` を使う。ライブラリとして使うだけなら `default-features = false` で外せる。
  - 読み込みでは、属性の accessor の型(POSITION/NORMAL は VEC3 f32、TEXCOORD_0 は VEC2 の f32 か正規化整数、JOINTS_0/WEIGHTS_0 は VEC4、indices はスカラー、morph target の POSITION/NORMAL は VEC3 f32)と数(POSITION と同じ)を読む前に確かめ、合わなければエラーにする(gltf クレートの assert による panic を避ける)。ノードを辿るときは再訪(children の循環・親が複数)をエラーにする。bufferView も sparse もない accessor(仕様では「すべて 0」。UniVRM が変化のない morph target に出す)は、0 を詰めた bufferView を足して読む。16 ビットのテクスチャは上位 8 ビットだけを使う。
  - `Renderer::new` が途中で失敗したときは、作った GL オブジェクトを消してから返る。
  - `model`: glb の読み込み。ノードの変換とスキニング(バインドポーズ)を頂点に焼き込み、静止ポーズとして持つ。
  - `vrm`: `VRMC_vrm` を自前で読む(`specVersion` の確認と、expressions のプリセット/カスタム名 → morph target bind の対応だけ)。VRM 0.x(拡張 `VRM`)は「未対応」のエラーにする。
  - `render`: GLES での描画。Lambert の平行光源、baseColor テクスチャ(SRGB8_ALPHA8、ミップマップ)、深度テスト、OPAQUE / MASK(discard)/ BLEND(描画順の整列なし、深度書き込みなし)。カメラはバインドポーズの外接箱から、全身が収まる距離に自動で置く(+Z から -Z を見る)。
  - 表情: expression の weight から morph target を CPU で合成し、頂点バッファを `glBufferSubData` で更新する。`destroy(gl)` で GPU リソースをすべて解放する。
  - `synth`: 試験・計測用の合成 VRM 1.0(頭 = テクスチャ + morph target `blink`、胴、スキン付き三角形)。
- `vrm-bench`(`crates/miharashi-vrm/src/bin/vrm-bench.rs`): `Offscreen::with_fbo`(EGL surfaceless + FBO)に描いて計測する。`with_fbo` の FBO には深度がないので、クロージャの中で深度 renderbuffer(DEPTH24_STENCIL8)を付けて、終わったら外して消す(`miharashi-gpu` は変えていない)。

`vrm-runtime` / `vrm-spec` / `serde_vrm` は採用していない。Issue にある「比較して採否を記録する」は**まだ実施していない**(自前の解釈は expressions だけで足りたので、先に計測を進めた)。B に進む前に、保守状況・ライセンス・GPU 非依存性を確かめて追記する。

## 動かし方

VRM モデルはリポジトリに置かない。各自で**利用条件(再配布・商用・表示形態)を確認して**用意する。

```sh
cargo build --release
# 合成モデル(モデルの用意が要らない)
./target/release/vrm-bench --synthetic --size 1280x720 --frames 600 --png /tmp/vrm.png
# 実モデル
./target/release/vrm-bench --model /path/to/model.vrm --size 1920x1080 --pci 0000:10:00.0 --png /tmp/vrm.png
```

| 引数 | 内容 |
|---|---|
| `--model <path.vrm>` / `--synthetic` | 読み込むモデル / 合成モデル(`--segments` で三角形数、`--texture` でテクスチャの 1 辺) |
| `--pci` | 描く GPU の PCI アドレス(既定 `0000:10:00.0` = 内蔵。NVIDIA は `0000:01:00.0`) |
| `--size` | `1280x720`(既定)、`1920x1080` など |
| `--frames` | 計測するフレーム数(既定 600、そのほかに 5 フレームのウォームアップ) |
| `--seconds` | 指定すると、フレーム数ではなくこの秒数だけ描き続ける |
| `--fps` | 指定すると、各フレームのあと次のフレームの時刻まで sleep して間隔を保つ(例 30)。`--seconds` と組み合わせて、一定 fps での CPU 使用率を測る |
| `--expression` | 動かす expression(省略時は `blink` → `happy` → `aa` → morph のある最初のもの) |
| `--still` | weight を 1 に固定する(省略時は 2 秒周期で 0 → 1 → 0) |
| `--png` | 最後のフレームを PNG に保存(見た目の確認用) |

出力: `GL_RENDERER` / `GL_VERSION`(llvmpipe でないことの確認)、モデルの規模(メッシュ・三角形・テクスチャ・morph target)、初期ロード時間(ファイル読み込み + 解釈 / GPU 転送)、フレーム時間の平均と p95(毎フレーム `glFinish` で GPU の完了まで待つ)、morph の CPU 時間、プロセスの CPU 使用率(`getrusage`)、GPU メモリ(`mem_info_vram_used` と `mem_info_gtt_used`)。

## 確認したこと

| 項目 | 結果 |
|---|---|
| 内蔵 GPU で描けている(ソフトウェアレンダリングではない) | `GL_RENDERER` = AMD Radeon Graphics (radeonsi, raphael_mendocino, LLVM 19.1.7, DRM 3.61, 6.12.111)、`GL_VERSION` = OpenGL ES 3.2 Mesa 25.0.7(llvmpipe ではない) |
| 見た目 | PNG で、テクスチャ付きの頭・胴・スキン付き三角形が正しい向きと位置に描けていることを確認(合成モデル) |
| ノード変換・スキニング | 試験で、親ノードの移動と、関節の移動(スキンの三角形)が頂点に効いていることを確認 |
| 表情 | 試験で、`blink` の weight で頂点が動くこと、存在しない expression がエラーになることを確認 |
| VRM 0.x | 「未対応」のエラーになる |
| 解放 | 描画後に `destroy` と深度 renderbuffer の削除を呼び、GL エラーが出ない |

## 計測結果(合成モデル、2026-10-18、release ビルド、各 600 フレーム)

| モデル | 解像度 | フレーム平均 / p95 | morph の CPU | プロセス CPU | ロード(ファイル+解釈 / GPU 転送) |
|---|---|---|---|---|---|
| 4,609 三角形、テクスチャ 1024² | 1280×720 | 0.07 / 0.08 ms | 0.004 ms | 52.7% | 5 ms / 8 ms |
| 320,001 三角形、テクスチャ 4096² | 1280×720 | 0.52 / 0.55 ms | 0.265 ms | 57.0% | 81 ms / 36 ms |
| 320,001 三角形、テクスチャ 4096² | 1920×1080 | 0.59 / 0.61 ms | 0.263 ms | 50.9% | 82 ms / 19 ms |

GPU メモリ(2 行目、`gtt` は描画前 139MB → 描画後 385MB、`vram` は 55MB のまま変化なし)。内蔵 GPU は GTT(システムメモリ)に載るので、約 246MB 増えた(転送した頂点・インデックス・テクスチャ約 93MB より多い。ドライバの確保単位や、`generate_mipmap`、深度バッファなどが含まれると考えられるが、内訳は未確認)。`destroy` 後も GTT がすぐには戻らない(プロセスが生きているあいだは Mesa が確保を持ち続ける)ので、解放の確認は GL エラーなしと、プロセス終了後の値で行う必要がある(後者は未確認)。

### 読み取れること

- 合成モデルでは、32 万三角形・4096² のテクスチャでも 1 フレーム 0.6 ms 前後で、720p / 1080p のどちらも 30fps(33 ms)の目標に対して大きな余裕がある。ただし球だけで構成した単純な形で、頂点は大半が小さく、**実モデルの重さ(髪・服の多層、BLEND の重なり、スキン、MToon)を代表しない**。実モデルの数値が出るまで、達成・未達の判断はしない。
- 1080p でもフレーム時間がほぼ増えない(0.52 → 0.59 ms)ので、この負荷では画素ではなく頂点側が支配的。
- morph の CPU 合成は 32 万頂点で 0.27 ms/フレーム。実モデルで morph を持つのは顔のメッシュ(数千〜数万頂点)だけなので、CPU 合成で足りる見込みだが、これも実モデルで確認する。
- **プロセス CPU 使用率の 50〜57% は、そのまま PoC-005 の目安に使えない**。この bench は `glFinish` を毎フレーム呼んで連続で描くので、待ちの間のドライバの CPU 消費を含み、計測時間も 0.3〜0.4 秒と短い。30fps に制限して一定時間走らせる計測は、下の「実モデルでの計測」で実施した(`--fps 30 --seconds 30`)。

## 実モデルでの計測(AI ニケちゃん、2026-10-18、release ビルド、内蔵 GPU)

- モデル: AI ニケちゃん `nikechan_v2.vrm`(tegnike/aituber-kit の `public/vrm/nikechan_v2.vrm`、元は tegnike/nikechan-assets の公式素材。非営利の個人利用・AI への入力は許可、**再配布・同梱は禁止**)。**AI ニケちゃん(非公式ファンメイドとしての技術検証)であり、モデルはリポジトリに同梱しない**(`.gitignore` に `*.vrm` を足した)。
- 取得手順(リポジトリの外に置く):
  ```sh
  mkdir -p ~/.cache/miharashi/vrm
  curl -fL -o ~/.cache/miharashi/vrm/nikechan_v2.vrm \
    https://github.com/tegnike/aituber-kit/raw/main/public/vrm/nikechan_v2.vrm
  ./target/release/vrm-bench --model ~/.cache/miharashi/vrm/nikechan_v2.vrm --png /tmp/nikechan.png
  ```
- 規模: VRM 1.0、メッシュ 4、プリミティブ 14、頂点 81,647、三角形 141,746、マテリアル 13、morph target 58、テクスチャ 16 枚(256×512 が 1、512² が 13、1024² と 2048² が各 1)、ファイル 約 23MB。expression は 29 個が morph bind を持つ(aa / blink / happy / lookDown など)。
- ロード: ファイル読み込み + 解釈 61〜63 ms、GPU 転送 10〜12 ms(転送 47MB)。
- 初回は読み込みが 2 か所で失敗し、直した(合成モデルでは出なかった形): ①bufferView のない accessor(変化のない morph target の「すべて 0」)、②16 ビット(R16G16B16A16)のテクスチャ。

| 解像度 | 条件 | フレーム平均 / p95 | morph の CPU | プロセス CPU |
|---|---|---|---|---|
| 1280×720 | `--frames 600`(連続描画) | 0.29 / 0.31 ms | 0.062 ms | 32.2%(cpu 0.06 s / wall 0.18 s) |
| 1920×1080 | `--frames 600`(連続描画) | 0.38 / 0.39 ms | 0.063 ms | 25.7%(cpu 0.06 s / wall 0.23 s) |
| 1280×720 | `--fps 30 --seconds 30`(900 フレーム) | 1.87 / 2.20 ms | 0.133 ms | **1.2%**(cpu 0.36 s / wall 30.00 s) |

- GPU メモリ(1280×720): `gtt` は描画前 139MB → 描画中 291MB(1920×1080 は 302MB)、`vram` は 55MB のまま。
- 30fps に制限した 30 秒で、プロセスの CPU 使用率は 1.2%(`glFinish` の待ちを含む。表情の weight を 2 秒周期で動かして morph の合成・転送もしている)。連続描画の 25〜32% は計測時間が 0.2 秒と短く、待ちの間のドライバの CPU 消費を含むので目安にしない。
- 30fps 制限ではフレーム時間が連続描画(0.29 ms)より長い(1.87 ms)のは、GPU が間隔の空いた負荷では低いクロックに落ちるためと考えられる(未確認)。どちらも 33 ms の予算の 6% 以下。
- 見た目(1280×720 の PNG を目で確認): 正面を向いた T ポーズの全身が、画面中央に縦いっぱい(余白は左右)で描けている。顔・髪(紫)・T シャツ(「AITuber」の文字)・ショートパンツ・靴まで、**テクスチャが乗っていて、欠けている部位や裏返しの面はない**。髪はバインドポーズのまま(揺れなし)、目や肌の陰影は Lambert のみで MToon の輪郭線・リムライトはない(AITuberKit とは見た目が違う)。
- GPU 使用率(`gpu_busy_percent`)は測っていない。

## 未対応(今回の範囲外)

- **スキニング(アニメーション)**: バインドポーズの 1 回だけ頂点に焼き込む。ボーンを動かしての変形(CPU か GPU か)は未実施。
- **MToon**: 使わない。`VRMC_materials_mtoon` は読まず、Lambert + baseColor のみ(見た目は AITuberKit とは違う)。
- **SpringBone**(髪・服の揺れ)、**LookAt**(視線)、**humanoid**: 読まない。
- **VRM 0.x**: エラーにする(拡張 `VRM`)。0.x と 1.0 の互換性は別に検証する。
- そのほか: baseColor 以外のテクスチャ(法線・emissive)、`KHR_texture_transform` などの拡張、頂点カラー、`TEXCOORD_1`、モデルの表示サイズ・向きの個別調整、画面への組み込み。

## 未対応・次の手順(B の前に直す)

読み込みの防御は、確かめられる範囲で入れた(上の「作ったもの」)。残りは次のとおり。

- accessor の型は、KHR_mesh_quantization のような整数の POSITION / NORMAL(i8・i16)を**未対応(エラー)**として弾いているだけで、読む対応はしていない。TEXCOORD_0 の整数は正規化のときだけ読む。
- sparse の accessor は gltf クレートに任せている。範囲外の sparse index を持つ壊れた glb での挙動は未確認。
- `JOINTS_1` / `WEIGHTS_1`(5 本以上の関節)、`TEXCOORD_1`、頂点カラーは読まない(JOINTS_0 の 4 本まで)。
- テクスチャは 1 枚が 2048² でも読めたが、巨大な画像(幅 × 高さが非常に大きい)を弾く上限は設けていない。
- 実モデルは 1 つ(ニケちゃん)だけ。ほかの VRM 1.0(別のツールで出したもの)での確認は B の前に増やす。

## 次の手順

1. 実モデルで足りない見た目(MToon の簡易版、法線・emissive)を検討する。
2. GPU の使用率(`gpu_busy_percent`)を測り、PoC-005 の目安値を決める(CPU 使用率は 30fps で測定済み)。
3. `vrm-runtime` などとの比較結果を記録する。
4. ボーンの簡単な変形(CPU スキニング)のコストを測る。
5. #74 の「画面に GL を貸す口」が決まったら、`miharashi-app` 側に `Screen` を実装する薄い部分を足す(B)。
