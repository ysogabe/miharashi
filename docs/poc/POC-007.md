# PoC-007 画面向け GLES 3D 描画境界(Issue #74)

目的: 画面が GLES で 3D を描くための口(`GlScene`)と、それを Compositor・ScreenManager・runtime が受ける境界を、VRM に依存しない回転する立方体(キューブ画面)で確かめる。本Issue: [#74](https://github.com/ysogabe/miharashi/issues/74)。設計は [Screen Plugin API v2](../DESIGN-screen-plugin-v2.md)(Issue #72)。VRM を載せるのは [#71](https://github.com/ysogabe/miharashi/issues/71) の B で、ここでは扱わない。

> **この文書の読み方**: 実機の数字は 2026-10-19、Ryzen 7 9700X の内蔵 GPU(radeonsi raphael、Mesa 25.0.7)、29UM59-P(HDMI-A-1)での値。**画面の絵は目で見ていない**(作業者が画面を見られない)。崩れ・残像・状態漏れの確認は、オフスクリーンの画素比較のテストで代えた。API の約束の詳細は設計書にあり、ここでは要点とリンクだけを書く。

## 作ったもの

- `crates/miharashi-glscene`(新クレート。依存は `glow` だけ。Linux 以外でも `cargo check` が通る)
  - `GlScene`(`draw` / `release`)、`GlTarget`、`Region`、場面が作った GL オブジェクトの作成 − 削除を数える `ObjectCount`。
- `miharashi-gpu`
  - `Compositor` に 3D の層(色 + 深度の FBO)・`reset_gl_state`・`draw_scene` を足した。`restore_gl_state` の役目を移した。`Frame` は変えていない。
  - `SceneFrame` / `GlesDisplay::present_scene` / `release_scenes`。オフスクリーンでも同じ経路を通る。
- `miharashi-app`
  - `Composite::Gl` と、最上段の重ね絵(`Top`)。`runtime.rs` の変換(`frame_of` / `scene_frame`)。
  - `Screen::needs_gl` / `gl_scene` / `scene_animating` / `frame_interval`、`App::gl_scenes` / `report_scene_failure`。GL の可否は `Output.gpu_max_texture.is_some()` を `kiosk()` から ScreenManager へ渡す。
  - 画面: キューブ(`cube` = 全面、`cube-third` = 画面中央の 1/3 幅)、状態をわざと汚す試験画面(`dirty-a` / `dirty-b`)。
  - 設定 `[cube]`(`enabled` / `layout` / `fps`)と `[gl_check]`(`enabled`)。
  - `miharashi bench-scene`(`gpu_bench.rs`): オフスクリーンで層の費用を測る。
  - `png --renderer gles` で `cube-gles.png` / `cube-third-gles.png`、GL なしでは案内の fixture(`scene-notice.png`)を出す。

## API の契約の要点

詳細は設計書(§2 口、§3 解放、§4 重ね方、§5 GPU 状態、§6 CPU 経路、§9 失敗、§10 描き直し)。

**画面(`GlScene`)の責任**

- `draw` は初回に GL オブジェクトを作る(遅延・冪等)。出力は premultiplied alpha。失敗は `Err(String)`。
- 開始した query・transform feedback・debug group など、Compositor が設定し直せないものは `draw` の中で閉じる。GL の状態を「戻す」責任は持たない。
- `release` は自分が作ったものだけを消す。`draw` の作りかけで失敗したあとにも呼ばれるので、作っていないものは消さない。呼んだあとの `draw` で作り直せること。
- Compositor・ScreenManager が 1 つの場面に呼ぶ `release` は**高々 1 回**(失敗してその場で呼んだ場面は終了時に呼ばない)。場面の側も 2 回目に耐える書き方にする。
- sampler を `draw` の前に解除するのは**ユニット 0〜15** まで。16 以降を使う場面は自分で sampler を設定する。

**Compositor の責任**

- `reset_gl_state` で、自分の描画の前と 3D を呼ぶ前に、framebuffer・viewport・scissor・テスト・マスク・blend・pixel store・sampler などを毎回既定値へ設定し直す。層は `(0,0,0,0)`・深度 1.0・ステンシル 0 で消してから渡す。`draw_scene` の中で 2 回呼ぶ。
- **戻さないもの**(理由は設計書 §5.1): clear 色(`draw_scene` が消去の前に決める)、uniform の値、インデックスつきのバッファ束縛、描画結果に効かない汎用の buffer 束縛、使う画面のないマルチサンプル系、既定の VAO の属性配列、レンダーバッファの bind、開始済みの query など。
- 3D の画面の `draw` が panic・`Err`・GL エラーになっても、そのフレームは下地とアラート・メニューで完成させ、キオスクは止めない(`catch_unwind`)。

**失敗と CPU 経路**

- 失敗したら**再起動まで 3D を出さない**(再試行は v1 に入れない)。画面 id つきで 1 回だけ `eprintln!` し、状態ログの `scene_fail=` に回数を出す。GL の可否・失敗が変わったときは `force_overlay` と `invalidate()` で、アラートが消えないようにする。
- `renderer = cpu` や GL なしの `auto`、失敗中は、3D の画面が案内(`notice::gpu_required`)になり、巡回から外れる。`scene_animating()` を内側の画面に混ぜないので、動かない写真を毎フレーム CPU で描き直さない。

**時間**

- 消灯・非表示では動きを止める(`set_presentation`)。復帰で溜まった動きをまとめて再生しない。
- `Screen::frame_interval() -> Option<Duration>`(既定 None = vsync)。動いている間だけ、runtime が表示の完了後に `frame_wait` で残りを待つ。

## 動かし方

```toml
[cube]
enabled = true
layout = "both"   # full(id = cube)/ third(cube-third)/ both
fps = 30          # 0〜240、0 = 制限せず vsync だけ。既定 30

[gl_check]
enabled = true    # dirty-a / dirty-b(実機の確認用。通常は使わない)
```

画面の id(`cube` / `cube-third` / `dirty-a` / `dirty-b`)は `ui.start_screen` と `rotation.steps` に書ける。`ui.refresh_screens` に書くと、今までどおりエラーになる。

```sh
# PNG(GL の画面は gles のときだけ描ける。なければ案内の fixture)
./target/release/miharashi png --renderer gles --out work/out   # cube-gles.png / cube-third-gles.png

# オフスクリーンのベンチ(実モニターは使わないので、キオスクを止めなくてよい)
./target/release/miharashi bench-scene [--size WxH] [--frames N] [--fps N] [--seconds N]
```

**実機のモニターで試すとき**: 本番のキオスクを止め、`seat = "direct"` で動かし、終わったら戻す。試験用の設定からは **`[screen_power]` を外す**(HA の消灯の設定を書き換えないため。このため実機での消灯・復帰は試していない)。

### メモリ(25 分、巡回 cube / photo / cube-third / photo / dirty-a / agents / dirty-b / photo を 5 秒ごと = 約 300 回切り替え)

| 項目 | 結果 |
|---|---|
| gl_objs(場面内の作成 − 削除) | 全部の GL 画面が一度出たあとは **24 で一定**(210 行)。最初は画面が初めて出るたびに 3 → 6 → 15 → 24 と増えた |
| RSS | 150 秒後から 322〜323MB で横ばい(終わりまで) |
| VRAM+GTT(システム全体の iGPU の値) | 最初の 150 秒を除き 450 秒ごとの 3 区間で、平均 230 / 209 / 200 MiB(最小 197 / 172 / 172、最大 331 / 291 / 292)。増え続けていない。キオスクを止めているときは約 37MiB |
| cube ↔ photo を 5 秒ごと 20 分 | gl_objs = 3 のまま一定(119 回の stats)。RSS は 250 → 272MB で、2 分後から 272〜273MB で横ばい |
| 8 画面を 10 ステップで 5 秒ごと 5 分(dirty-a / photo / dirty-b / agents / aircraft / cube / cube-third / status) | GL エラー・場面の失敗なし。RSS は 240 → 329MB(初めて出す画面の読み込み。5 分では横ばいに届かず、上の 25 分の試験で横ばいを確認) |

VRAM+GTT は写真の読み込みで上下するので、「増えない」の根拠は区間ごとの平均が下がっていることと gl_objs の一定による。

### 読み取れること

- **30fps 上限でキューブ全面の iGPU は約 6.5%、60fps では約 14%**。fps を半分にすると iGPU は 2560x1080・1080p ではほぼ半分、720p では 6 割(4.2% 対 7.0%)になる。この結果から、キューブの既定を 30fps にした。
- **層(色 + 深度の FBO)を挟む費用は、30fps 間隔で全面 2560x1080 が約 1.1ms**(draw_scene 1.27 − 直接 0.15。直接にも全画面の消去を含めた)。30fps の予算 33ms の 3〜4%。連続描画では 0.37 と 0.04 で、差は 0.3ms ほど。1080p 全面は 0.96ms(30fps 間隔)、720p 全面は 0.53ms。`reset_gl_state` は 3 回でも 0.00ms で、無視できる。このため `Direct` モード(標準の framebuffer へ直接描く)は足さない。
- 30fps 間隔のほうが連続より GPU 時間が長いのは、GPU のクロックが下がるため。実際の運用(30fps)に近いのは前者。
- **1/3 幅の CPU 3.4% は、下地の毎フレームの CPU 描画と全画面の転送が原因**と考えられる(全面のキューブは 1.2%、写真は 0.5%)。ベンチでも下地ありの 1/3 幅は下地なしより GPU が 0.7ms ほど長い(30fps 間隔、1.34 対 0.61)。下地が変わったときだけ描く `base_changed`(設計書 §10)で減らせる見込み。ただし**減らせる量は未確認**(推測)。
- 1920x1080 の 30fps(iGPU 7.9%)が 2560x1080(6.5%)より高いのは、画素数と合わない。クロックの揺れの範囲と**見ているが、確かめていない**(60fps では 14.0% と 14.3% でほぼ同じ)。
- 720p は 30fps で 4.2%、60fps で 7.0%。
- 同じ写真画面の iGPU 0.8% に比べ、キューブは 30fps でも 6.5% かかる。常時動く 3D を出す費用として、VRM(#71 B)でも見積もりに使う。
- メニューの出し入れの 1 フレーム(24〜25ms)は、30fps の 1 フレーム(33ms)に収まるが、`Upload` が 1 フレームに集中する。

## 制限事項と #71 B への申し送り

- **`base_changed` は未実装**。下地が `Canvas`(アラート・メニュー表示中の Agent、最初の 1 枚が出るまでの写真)のとき、3D を描くたびに下地の全画面 CPU 描画と転送が走る。1/3 幅の CPU 3.4% はこれが原因と見られる。#71 B で Agent + VRM の CPU 使用率を測って要否を決める。
- **`frame_wait` の待ち方は 60Hz の 30fps だけ確認した**(間隔 − vsync の半分だけ待つ。そうしないと 30fps が 20fps になる)。他のリフレッシュレート(50Hz・144Hz など)は未確認。
- Compositor の層と最上段の重ね絵のテクスチャは **gl_objs に入らない**(`GlScene` 内の作成 − 削除だけを数える)。それらの増減は VRAM+GTT で見る。
- メニューの出し入れで、最上段の重ね絵の `Upload` に 1 フレーム 24ms ほどかかる。アラート・メニューが出ている間は、1 秒ごとの時計の更新でも `Upload` が走る(設計書 §4.1)。
- GPU のリセット(context lost)は扱わない。起きたら §9 の失敗の扱いに入り、再起動まで 3D を出さない。
- 3D の失敗後の再試行はしない(再起動まで)。
- MSAA はない(層はマルチサンプルでない)。
- `Cargo.toml` に `panic = "abort"` が無いことを確かめる単体テストは、まだ足していない(`catch_unwind` が効く前提)。
