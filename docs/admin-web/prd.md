# Web 管理ページ PRD

作成: 2026-10-30。Issue: [#94](https://github.com/ysogabe/miharashi/issues/94)(Web 管理ページ)。設計は [design.md](design.md)。レビュー(Sol、Opus の安全面)の反映: 2026-10-30。

## 背景と目的

Miharashi の設定は `/etc/miharashi/config.toml` に書き、変えるには SSH でログインして TOML を編集し、サービスを再起動している。日々いじるのは、ほとんどが「接続先のサーバーが変わった」「この画面はしばらく出さない」の 2 種類で、これらを机の上のブラウザから済ませたい。

当初の [PRD](../PRD.md) §10 では「遠隔 Web 管理画面」を初期の範囲外にしていた。操作パネル(Echo Show 5)向けの HTTP API([docs/panel/DESIGN.md](../panel/DESIGN.md))が本番で動いている今、その上にページを 1 枚足す形なら小さく作れるので、範囲に入れる。

## 使う人と場面

- 使う人は作者 1 人。自宅の LAN にいる PC かスマートフォンのブラウザから使う。
- 場面:
  - GEOFRAME(写真サーバー)や T3 Code のサーバーを別のポートや別の IP に動かしたとき、接続先を変える。
  - 航空機の受信機を止めている間、航空機の画面を出さないようにする。T3 Agent の画面や試験用の画面(キューブ・VRM)を出す・消す。
  - 「写真が止まっているのは GEOFRAME が落ちているのか、キオスクの設定が違うのか」を、SSH せずに見分ける。
  - トークンのファイルが置けているか、権限がおかしくないかを確かめる。
- キオスクの日常の操作(画面の切り替え・モニターの消灯)は、これまでどおり操作パネルで行う。管理ページは設定と状態のためのもので、操作盤の代わりではない。

## ゴール / やらないこと

ゴール:

- 接続先の URL と画面の有効/無効を、ブラウザで見て、変えて、再起動で反映できる。
- 管理ページから保存した値が原因で、キオスクが起動できなくなることがない(SSH で設定ファイルそのものを壊した場合は今までどおり起動しない。これは管理ページの守る範囲の外)。
- 管理トークンが盗まれても、HA のトークンや T3 のトークンが攻撃者のサーバーへ送られることはない。
- 取得元ごとの接続状態とトークンファイルの状態が、1 ページで分かる。

やらないこと(今回の範囲外):

- 設定ファイル全体の編集。巡回の手順、タイル、焼き付き対策、表示先 GPU などは TOML のまま。
- **Home Assistant の URL を管理ページから変えること**(表示だけ)。HA のトークンは家の機器を操作できるので、送り先は root 所有の設定ファイルでしか変えられないままにする(安全面のレビューの結論)。
- T3 の URL を、設定ファイルで許したホスト以外へ向けること。新しいホストは SSH で設定ファイルに足す。
- トークンの値(HA・T3・GEOFRAME・パネル・管理ページ)をブラウザから入力・保存すること。トークンはこれまでどおり SSH でファイルに置く。
- 設定の再読み込み(再起動なしでの反映)。反映は再起動で行う。
- `/etc/miharashi/config.toml` を書き換えること。保存先は実行ユーザーが書ける別のファイルにする。
- 操作パネルの機能(キー・画面の直接選択・モニター・巡回)を管理ページに置くこと。
- ログ(journal)の表示。
- LAN の外(Tailscale や公開インターネット)からの利用。HTTPS。複数ユーザーや権限の区別。
- `[panel] enabled`・`[rotation] enabled` の切り替え。前者は自分を締め出す。後者は画面ではなく、実行時の停止・再開 API が別にある。
- T3 のトークンを別の T3 サーバーに対して発行すること。トークンを作る t3 CLI は、ペアリング済みの自分のサーバーにしか発行できない。

## 要求

- R1(必須): LAN のブラウザで管理ページを開ける。ページはパネルの HTTP サーバーが配信し、別のプロセスやポートは増やさない。
- R2(必須): 管理ページ用のトークンで認証する。トークンはパネルのものと別のファイルに置き、値も別にする。パネルのトークンで管理 API は呼べず、管理ページのトークンで既存のパネル API は呼べない。
- R3(必須): 次の項目の「今効いている値」「設定ファイルの値」「上書きの値(あれば)」「次回起動の値」を見られる。
  - 変えられる接続先: `geoframe.url`、`agents.url`、`aircraft.url`
  - 表示だけの接続先: `home_assistant.url`
  - 変えられる画面の有効/無効: `aircraft.enabled`、`room.enabled`、`agents.enabled`、`cube.enabled`、`vrm.enabled`
- R4(必須): R3 の「変えられる」項目を保存できる。保存先は実行ユーザーが書ける「上書きファイル」で、`/etc/miharashi/config.toml` は変えない。保存前に、**その時点の**設定ファイルと上書きを合わせた全体を今と同じ規則で検証し、通らなければ保存せず理由を返す。設定ファイルがその時点で読めない・検証に通らないときも保存しない。
- R5(必須): 上書きにある URL は、画面が無効でも必ず検査する。`agents.url` のホストは、設定ファイルの `[admin] allowed_hosts` にあるか、設定ファイルの `agents.url` と同じホストだけを認める(ポート・パス・http と https の違いは自由)。4 つの URL とも、ユーザー名・パスワード、制御文字、空白、引用符を含むものは拒否する。
- R6(必須): 項目ごとに上書きを取り消して設定ファイルの値に戻せる。
- R7(必須): 「再起動して反映」ボタンがある。「再起動すると値が変わる」状態(保存したが再起動していない)がページで分かる。短い間に続けて再起動できず、通常の管理操作だけでは systemd の起動制限に掛からない。
- R8(必須): 上書きファイルが読めない・検証に通らないときも、キオスクは設定ファイルだけで起動する。無視した理由はログと管理ページに出る。
- R9(必須): 上書きを使って起動した直後(60 秒以内)に異常終了したら、次の起動では上書きを外して設定ファイルだけで起動し、理由をログと管理ページに出す(上書きが原因で起動を繰り返し、systemd が止めてしまうのを防ぐ)。正常終了(SIGTERM、キー、管理ページの再起動)は対象にしない。
- R10(必須): `check-config` と起動時のログに、上書きが効いていること(何項目を上書きしたか)が出る。
- R11(必須): 取得元ごとの接続状態が見られる。GEOFRAME、Home Assistant(室内センサー)、気象庁(予報)、気象庁(警報)、tar1090(航空機)、T3(エージェント)。取得処理の状態(動いていない・初回の取得前・正常・失敗中)と、最後に取得できた時刻、直近のエラーの短い説明のうち、その取得元が持っているもの。画面の有効/無効とは別に出す。
- R12(必須): トークンファイル(HA・T3・パネル・管理ページ)について、ファイルがあるか、開けるか、所有者と権限が規則どおりかを見られる。値は出さない。
- R13(必須): 上書きで変わる設定の値を、キオスクの外のスクリプトからも同じ規則で取れる。`miharashi-t3-token`(T3 のトークンを週 1 回作り直すスクリプト)は、この口から T3 の URL を取り、接続の確認に使う(今は設定ファイルを `sed` で読んでいる)。
- R14(必須): ホスト名、バージョン、起動からの時間、今の画面が見られる。
- R15(必須): 保存は、ページが読み込んだ時点の上書きファイルに対して行い、その間に別のタブや SSH で上書きファイルが変わっていたら保存せずに知らせる。入力中の値は、定期的な状態の更新で消えない。
- R16(必須): 管理ページの処理(本文の受け取り、保存、応答)が遅くても、操作パネルのキー操作は待たされない。
- R17(必須): 他のサイトから開いたページが、管理 API を呼べない(CSRF が成り立たない)。Cookie を使わず、状態を変える経路はすべて `Authorization` ヘッダーを要し、CORS のヘッダーを返さず、トークンを URL で受け取らない。
- R18(あると良い): 接続先ごとに「疎通確認」ボタンがあり、入力中の URL にキオスクから届くかを試せる。
- R19(あると良い): T3 のトークンの権限(scope)と期限が見られる。
- R20(あると良い): 設定ファイルの最終更新時刻が見られる(SSH で直したあと再起動していない、に気づける)。

## 受け入れ条件

- AC1(R1): `[panel]` と `[admin]` を有効にしたキオスクに対し、LAN の別の端末のブラウザで `http://<listen>/admin` を開くとページが表示される。外部のスクリプト・フォント・画像は読み込まない(ブラウザの開発者ツールで `listen` 以外への通信が無い)。応答に CSP・`X-Frame-Options`・`nosniff`・`no-store` のヘッダーが付く(単体テスト)。
- AC2(R2): 管理トークン無しで管理 API を呼ぶと 401。パネルのトークンで管理 API を呼ぶと 401。管理トークンで `POST /api/v1/input` を呼ぶと 401。管理トークンのファイルが規則(所有者・権限・長さ)を満たさない、またはパネルのトークンと同じ値なら、起動時にその旨を stderr(journal)に出して管理ページだけ無効になり、キオスク本体は起動する(この状態は管理ページから見えないので、journal で確かめる)。いずれも単体テストで確かめる。
- AC3(R3): 設定ファイルに `aircraft.url = A`、上書きに `aircraft.url = B` があるとき、管理 API は「効いている値 B、ファイルの値 A、上書き B、次回起動 B」を返す。上書きが無い項目は「上書き無し」と返す。`home_assistant.url` は `readonly` の印付きで値だけ返る。単体テストで確かめる。
- AC4(R4): 設定ファイルが `agents.enabled = true` と `ui.start_screen = "agents"` の正しい状態で、上書きに `agents.enabled = false` を保存すると 400 になり、本文に `validate` と同じエラー文「ui.start_screen = agents には agents.enabled = true が必要」が入る。上書きファイルは変わらない。単体テストで確かめる。
- AC5(R4): 保存に成功すると上書きファイルが置き換わる。置き換えの途中のどの時点で止めても、上書きファイルは「前の内容」か「新しい内容」のどちらかで、消えたり壊れたりしない。直前の内容は `.prev` に残る。単体テスト(一時ファイルを書いた直後・`.prev` を作った直後で止めた状態を作り、読み直す)で確かめる。
- AC6(R4、R5): 次はすべて 400 で拒否され、上書きファイルは変わらない(単体テスト): 外側の知らないキー(`panel.listen`)。内側の知らないキー(`agents.token_file`、`geoframe.photo_interval_secs`)。`home_assistant.url`(表示だけ)。URL のユーザー名・パスワード(`http://u:p@192.0.2.1/`)。空白・引用符・制御文字を含む URL。`agents.enabled = false` のままでも、`agents.url` の形が不正。`agents.url` のホストが許可されていない(`allowed_hosts` にも、設定ファイルの `agents.url` にも無い)。
- AC7(R5): 設定ファイルの `agents.url` が `http://192.0.2.30:3773`、`allowed_hosts = ["t3.example.test"]` のとき、上書きの `agents.url` に `http://192.0.2.30:4000`、`https://t3.example.test/` は保存でき、`http://192.0.2.31:3773` は 400。起動時の読み込みも同じ規則で、許されないホストの上書きは無視して理由を出す。単体テストで確かめる。
- AC8(R4): 保存の時点で設定ファイルが読めない・検証に通らないと 409 になり、上書きファイルは変わらない。単体テストで確かめる。
- AC9(R6): ある項目の上書きを取り消して保存すると、上書きファイルからそのキーが消え、管理 API の「次回起動の値」は設定ファイルの値になる。全部取り消すと上書きファイルは消える(`.prev` は残る)。単体テストで確かめる。
- AC10(R7): `POST /api/v1/admin/restart` でキオスクが終了コード 0 で終わり、systemd が再起動する。起動から 120 秒以内の要求は 429 で拒否され、本文に待ち時間が入る。一度受け付けたあと終了するまでの要求も 429。終了は単体テスト(実行ループに届くこと、2 回目が 429)、再起動は実機で確かめる。モニターが消えている間に再起動しても、再起動後の点灯・消灯が設定どおりになる(実機)。
- AC11(R7): 「再起動すると値が変わる」(`pending_restart`)は、「今の上書きファイルを今の設定ファイルに重ねて、起動時と同じ規則で求めた次回起動の値」が「今効いている値」と違うときだけ `true`。次の 4 通りを単体テストで確かめる: 効いている値を変える保存 → `true`。効いている値と同じ値の保存 → `false`。上書きを取り消して設定ファイルの値が効いている値と同じ → `false`。上書きファイルが壊れている → 警告は出るが、`pending_restart` は上の規則どおり(効いている値が壊れる前の上書きから来ていれば `true`)。
- AC12(R8): 上書きファイルが TOML として壊れている、知らないキーがある、合わせた設定が検証に通らない、の 3 通りで、キオスクは設定ファイルだけで起動し、stderr(journal)に理由を 1 行出す。管理 API の `overlay.error` に同じ理由が入る。単体テストで確かめる。
- AC13(R9): 上書きを使って起動したときに印のファイルが置かれ、60 秒たつと消える。印が残った状態で起動すると、上書きを無視して理由(「前回の起動が 60 秒以内に終わった」)を出す。正常終了の経路(SIGTERM、管理ページの再起動)では印が消える。単体テスト(印の読み書きと判定)と実機(上書きで起動 → 60 秒以内に `kill -9` → 次の起動のログ)で確かめる。
- AC14(R10): `miharashi check-config` が、上書きが効いているときに「上書き: <path>(<n> 項目)」と効いている値を出す。上書きファイルが無いときは何も出ない。無視したときは理由を出し、終了コードは 0。単体テストで確かめる。
- AC15(R11): 取得元ごとに、設計の対応表どおりの状態が返る。GEOFRAME を止めると `failing` になり、再開すると `ok` と最後に取得できた時刻が出る。`room.enabled = false` でも警報の取得は `ok` のまま(画面と取得は別)。T3 のトークンが無いときは `auth_required`。実機(または模擬サーバー)で、各取得元の取得間隔の 2 倍まで待って確かめる。
- AC16(R12): トークンファイルが無い、開けない、所有者が違う、権限が緩い(その他に読み取り)、規則どおり、が区別されて返る。値は返らない。単体テストで確かめる(所有者違いは、テストを root で動かさないので `uid` を偽の値にした判定関数で確かめる)。
- AC17(R13): `miharashi config-get agents.url --config <file>` が、上書きがあればその値、無ければ設定ファイルの値を出し、起動時と同じ規則(壊れた上書き・許されないホストは無視)で求める。知らないキーは終了コード 1。単体テストで確かめる。`miharashi-t3-token` は関数の定義と本処理を分け、関数のテストで `t3` と `curl` が呼ばれないことを確かめる。
- AC18(R13): 保存して再起動する前にトークンの更新が走っても、接続の確認は次回起動の URL に対して行い、届かなければトークンを置き換えない(今と同じ安全側の動き)。スクリプトの関数のテストで確かめる。
- AC19(R14): ページにホスト名・バージョン・起動からの時間・今の画面が出て、タブが見えている間は 5 秒程度で更新される。実機で確かめる。
- AC20(R15): 保存は読み込んだ時点の「世代」を付けて送り、上書きファイルがその後に変わっていれば 409 で保存されない。単体テストで確かめる。定期更新中に入力欄の内容が消えないことは実機で確かめる。
- AC21(R16): 本文を途中までしか送らないクライアントが `PUT` を開いたままでも、`POST /api/v1/input` が 1 秒以内に応答する。単体テストで確かめる。
- AC22(R17): `Origin` ヘッダー付きで `Authorization` の無い `PUT /api/v1/admin/config` と `POST /api/v1/admin/restart` は 401。`OPTIONS` は 405 か 404。どの応答にも `Access-Control-Allow-*` が無い。`?token=` のようなクエリでトークンを渡しても 401。`app.js` に `innerHTML`・`insertAdjacentHTML`・`document.write` が無い(文字列の検査)。単体テストで確かめる。
- AC23(R18、あると良い): 疎通確認は 3 秒で諦め、結果(HTTP の状態か、届かなかった理由)を返す。応答を保留する模擬サーバーに対して 3 秒前後で返ることと、確認中の `POST /api/v1/input` が 1 秒以内に応答すること、`Authorization` ヘッダーを送らないこと、リダイレクトを追わないことを単体テストで確かめる。
- AC24(R19、あると良い): T3 のトークンの権限と期限が出る。記録が無いときは「不明」と出る。単体テストで確かめる。
- AC25(R20、あると良い): 設定ファイルの最終更新時刻が出て、SSH で書き換えると次の更新で変わる。実機で確かめる。
- AC26(全体): 既存の `cargo test` が全部通り、操作パネル(miharashi-panel)の動きが変わらない(`/api/v1/status` の内容と `schema_version` は変えない)。
- AC27(全体): LP・README・docs に管理ページのスクリーンショットを載せない。docs とテストの例に出す URL は `192.0.2.x`・`example.test` などの例示用だけにする(Issue #60、見本と例に実際の自宅情報が入っている件、に新しい事例を増やさない)。

## 制約

- 常駐するものは Rust で、既存の `miharashi-app` の中に作る(別プロセスの Node・Python は使わない)。
- HTTP サーバーは既存の `tiny_http`(`panel.rs`)を使い、待ち受けはパネルと同じ `listen`(LAN のインターフェースの IP。`0.0.0.0` は不可)に限る。
- 認証は既存のパネルと同じ `Authorization: Bearer`。平文 HTTP の LAN 内利用という前提はパネルと同じで、今回それより広げない。管理トークンの重みは「T3 のトークンの送り先を許可ホストの範囲で変えられる」「画面を消せる」「再起動できる」で、HA のトークンには届かない。
- キオスクは一般ユーザーで動き、`/etc/miharashi` には書けない。`systemctl` も呼べない(polkit・sudoers は置かない)。再起動は自分で終了して `Restart=always` に任せる。
- 設定の検証規則は今の `Config::validate` を使い、二重に持たない。上書きに固有の規則(許可ホスト、画面が無効でも URL を検査、文字の検査)は 1 か所に書き、読み込みと保存の両方から呼ぶ。
- `config.toml`(0644)にトークンの値を書かない方針は変えない。上書きファイルにも秘密を書かない(URL のユーザー名・パスワードも拒否する)。
- `/api/v1/status` の形と `schema_version` は変えない(操作パネルの互換)。

## 決まっていないこと

- 管理トークンの既定のパスを `/etc/miharashi/admin.token` にするか。パネルのトークンと並べる案で進める。
