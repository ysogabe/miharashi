02 / Transport

BLE キーボードか、
ネットワーク API か。

同じ条件で並べて比べ、
ネットワーク API を選びました。

A

BLE キーボード(HOGP)

付録に保持
  • Miharashi 側の変更なし。bluez を入れれば普通のキーボードとして evdev に出る(未検証)
  • Echo 側は素のキーボードレポートの送信と Report Map の作り直しが要り、再ペアリングになる
  • BLE は 1 ホストだけ。Codex 用の操作盤(Mac とボンド)と同じ端末では両立しない
  • 一方向。今どの画面かは手元に出ない
  • ホストに bluez の導入とヘッドレスのペアリング、再起動後の再接続の確認が要る
B

ネットワーク API(Wi-Fi)

採用
  • Echo 側は HTTP クライアントを足すだけ。ROM の変更も再ペアリングも不要
  • Codex 用の操作盤と同じ端末で同居できる(BLE は Mac、Wi-Fi は Miharashi)
  • 双方向。画面名、写真の n / N、将来の LLM・エージェント状態を手元に出せる
  • Miharashi に小さな待ち受けを足す。既定は無効、トークン、1 インターフェース限定
  • Echo の Wi-Fi の安定性は実機で測る(5GHz の不安定の報告あり)

決め手は 3 つ。同じ端末で同居できること、参考実装が一番苦労した priv-app・署名鍵・HID の復帰を避けられること、手元に状態を出せること。A 案は「やるなら何が要るか」を設計書の付録に残しています。

SAFETY

キオスクはコマンドを実行しない

API でできるのはキー操作、画面の指定、状態の読み出しだけ。設定で有効にしない限り待ち受けは立ち上がらず、0.0.0.0 は指定できません。パネルが消えてもキオスクは影響を受けません。

05 / Questions we expect

仮想FAQ

設計を確かめるための想定問答です。
実ユーザーの質問や、
対応済みの実績ではありません。

なぜ Echo Show 5 なのですか？

Android 化した Echo Show 5(960×480)を Codex 用の操作盤にした実装がすでにあり、常駐サービス、起動時の自動開始、Canvas で描く大きなボタン、押下音と触覚、設定画面が流用できるからです。

BLE キーボードにしなかったのはなぜですか？

Miharashi 側の変更がゼロという利点はありますが、BLE は 1 ホストだけなので Mac とボンドした同じ端末では両立せず、手元に状態も出せません。Report Map の作り直しと再ペアリングも要ります。設計書の付録に「やるなら何が要るか」を残しています。

キオスクに API を足して安全ですか？

既定は無効で、有効にしても Bearer トークンと 1 つのインターフェースに限ります。できるのはキー操作、画面の指定、状態の読み出しだけで、コマンドは実行しません。

Echo の Wi-Fi が切れたらどうなりますか？

パネルは STALE、15 秒で OFFLINE を表示して再接続を続けます。キオスクは影響を受けません。

スマホのブラウザーからも操作できますか？

同じ API なので、ブラウザー向けの小さなページも作れます。まずは Echo のネイティブアプリ(全画面、常時点灯)を優先します。

今すぐ使えますか？

現在は設計段階です。P1 で Miharashi 側の API を実装し、curl で確認したうえで P2 の Echo アプリに進みます。
