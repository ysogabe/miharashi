02 / Transport

BLE キーボードか、
ネットワーク API か。

同じ条件で並べて比べ、
ネットワーク API を選びました。

A

BLE キーボード(HOGP)

付録に保持
  • Miharashi 側の変更なし。bluez を入れれば普通のキーボードとして evdev に出る(未検証)
  • Echo を BLE 周辺機器にする実装(GATT、Report Map、ペアリング)を新規に書く
  • LineageOS では ROM の変更(priv-app、feature 宣言)と署名鍵の管理が要り、更新のたびに再ペアリングの危険がある
  • 一方向。今どの画面かは手元に出ない。Echo 以外からは使えない
  • ホストに bluez の導入とヘッドレスのペアリング、再起動後の再接続の確認が要る
B

ネットワーク API(Wi-Fi)

採用
  • Echo 側は HTTP クライアントだけ。通常のアプリで済み、ROM の変更も再ペアリングも不要
  • 双方向。画面名、写真の n / N、将来の LLM・エージェント状態を手元に出せる
  • Echo がなくても curl で検証でき、スマホのブラウザーや別の端末からも同じ API
  • Miharashi に小さな待ち受けを足す。既定は無効、トークン、1 インターフェース限定
  • Echo の Wi-Fi の安定性は実機で測る(5GHz の不安定の報告あり)

決め手は 3 つ。Echo 側が普通のアプリで済むこと、手元に状態を出せること、Echo がなくても検証できること。A 案は「やるなら何が要るか」を設計書の付録に残しています。

認証なしの生存確認だけ
SAFETY

キオスクはコマンドを実行しない

API でできるのはキー操作、画面の指定、状態の読み出しだけ。設定で有効にしない限り待ち受けは立ち上がらず、0.0.0.0 は指定できません。パネルが消えてもキオスクは影響を受けません。

APP

普通のアプリで、別のリポジトリに

priv-app にせず、ROM も変えません。権限は Wi-Fi と振動と自動起動だけ。Android のコードは miharashi とは別のリポジトリ miharashi-panel にゼロから書き、API の契約は設計書と /status の JSON 例で共有します。

05 / Questions we expect

仮想FAQ

設計を確かめるための想定問答です。
実ユーザーの質問や、
対応済みの実績ではありません。

なぜ Echo Show 5 なのですか？

960×480 の横長画面が机に置く操作盤にちょうどよく、Android 化すれば普通のアプリが動くからです。Miharashi 専用の単体アプリとして全画面・常時点灯で使い、ほかの用途との同居は考えません。

BLE キーボードにしなかったのはなぜですか？

Miharashi 側の変更がゼロという利点はありますが、Echo を BLE 周辺機器にするには ROM の変更(priv-app、feature 宣言)と署名鍵の管理が要り、更新のたびに再ペアリングの危険があります。手元に状態も出せません。設計書の付録に「やるなら何が要るか」を残しています。

アプリはどこで作りますか？

miharashi とは別のリポジトリ miharashi-panel で、ゼロから書きます。Rust のワークスペースに Android SDK や署名鍵を持ち込まないためです。API の契約は miharashi 側の設計書と /status の JSON 例で共有します。

キオスクに API を足して安全ですか？

既定は無効で、有効にしても Bearer トークンと 1 つのインターフェースに限ります。できるのはキー操作、画面の指定、状態の読み出しだけで、コマンドは実行しません。

Echo の Wi-Fi が切れたらどうなりますか？

パネルは STALE、15 秒で OFFLINE を表示して再接続を続けます。キオスクは影響を受けません。

Echo が再起動したらどうなりますか？

起動時に自動で前面に出て、/status を取り直します。アプリは状態を持たないので、落ちても殺されても同じ表示に戻ります。

スマホのブラウザーからも操作できますか？

同じ API なので、ブラウザー向けの小さなページも作れます。まずは Echo のネイティブアプリ(全画面、常時点灯)を優先します。

今すぐ使えますか？

現在は設計段階です。P1 で Miharashi 側の API を実装し、curl で確認したうえで P2 の Echo アプリに進みます。
